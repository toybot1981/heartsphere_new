# Design: 页面内容分析与 Cursor 分析工件

## Context

测试失败时仅靠错误信息和截图路径不足以让 Cursor 快速理解「页面实际返回了什么」。需要对失败时刻的页面内容做轻量分析，并输出一份结构化、可直接在 Cursor 中使用的上下文，便于 AI 分析异常原因并建议修复。

## Goals / Non-Goals

### Goals
- 在测试步骤失败时采集页面上下文：URL、可见文本摘要、与失败步骤相关的 DOM 片段、截图路径、预期 vs 实际
- 将「结果不正常」时的分析结果输出为 Cursor 分析工件（Markdown 优先，可选 JSON），便于在 Cursor 中打开或粘贴
- 在涉及数据增删改查的页面操作完成后，支持数据库验证步骤，通过查询数据库判断操作是否真正成功
- 支持测试计划分解为多个 task，每个 task 包含多个用例，便于分阶段执行和管理
- 用例执行状态持久化，执行成功后标记并保存状态，下次执行时自动跳过已成功的用例（除非用户指定重新测试）
- 不改变现有测试执行流程的入口与报告格式的兼容性，以「附加输出」为主

### Non-Goals
- 不调用 Cursor API 或任何 IDE 接口；仅生成文件/文本供用户或脚本使用
- 不做复杂 DOM 语义分析（如可访问性树）；以「可读摘要 + 原始片段」为主
- 不强制要求每次运行都生成 Cursor 工件；可在有失败时再生成
- 不实现复杂的数据库操作（如事务、存储过程调用）；仅支持 SELECT 查询验证
- 不自动推断需要验证的表和字段；需在测试计划中明确指定验证步骤
- 不实现复杂的 task 依赖关系或并行执行；task 主要用于组织用例，按顺序执行
- 不自动清理或重置用例状态；状态文件由用户手动管理或通过 `--force` 重置

## Decisions

### Decision 1: 「页面返回内容」的范围
**决策**：在失败步骤执行后立即采集：
- 当前页面 URL
- 页面标题（`document.title`）
- 可见文本摘要：body 内主要可见文本的前 N 个字符（如 2000 字符），或按区域截断，避免过大
- 与失败步骤相关的 DOM 片段：若步骤涉及选择器，则采集该选择器对应元素的 `outerHTML` 或父节点片段（带长度上限，如 3000 字符）
- 截图路径（已有）
- 失败步骤描述、预期结果、实际错误信息

**原因**：足够支撑「页面当时长什么样、断言期望什么、实际报什么错」的叙述，便于 Cursor 分析；同时控制体积，避免把整页 HTML 都塞进工件。

### Decision 2: 「结果不正常」的判定
**决策**：任一测试步骤状态为失败（如 `verify` 未通过、元素未找到、超时等）即视为结果不正常，触发页面内容采集与 Cursor 工件生成。

**原因**：与现有 test_executor 的失败语义一致，实现简单、行为可预期。

### Decision 3: Cursor 分析工件的格式与位置
**决策**：
- 格式：Markdown 为主（标题、步骤信息、预期/实际、页面摘要、DOM 片段、截图路径、使用说明），便于在 Cursor 中直接打开或粘贴到对话。
- 可选：同内容的 JSON 输出，便于脚本或后续工具消费。
- 位置：可由配置或命令行参数指定目录；默认可与测试报告同目录或固定子目录（如 `./cursor_analysis/`），文件名含时间戳与用例标识，如 `cursor_analysis_<case_id>_<timestamp>.md`。

**原因**：Markdown 对人和 Cursor 对话都友好；JSON 保留扩展性；路径可配置避免污染项目根目录。

### Decision 4: 与现有结果结构的关系
**决策**：在现有测试结果 JSON 中增加可选字段（如 `page_context` 或 `cursor_analysis_path`），用于保存采集的页面摘要与 Cursor 工件路径；报告生成器可选择性展示或引用该路径。不破坏现有字段结构。

**原因**：兼容现有报告与下游逻辑；新能力以附加形式存在。

### Decision 5: 数据库验证步骤语法与配置
**决策**：
- **步骤语法**：使用 `verify database: <SQL查询>` 或 `check database: <SQL查询>`，查询结果可通过断言验证（如 `verify database: SELECT COUNT(*) FROM users WHERE name='test'` 期望返回 1）
- **数据库配置**：优先从测试计划的 `database` 字段读取（host, port, database, username, password）；若无则从环境变量读取（DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD）；最后尝试默认值（localhost:3306, heartsphere, root, 123456）
- **验证时机**：在涉及增删改查的页面操作步骤（如 `click #save-button`, `type ... in #name`）之后，可添加数据库验证步骤
- **查询结果处理**：执行 SELECT 查询，将结果与预期值比较（如 COUNT(*) = 1, 某字段 = 'expected_value'）；验证失败时记录查询结果与预期值，并触发页面内容采集

**原因**：
- 页面操作可能显示成功但数据库未更新（事务未提交、异步延迟、错误被吞等）
- 通过数据库验证可确保数据真正持久化
- 使用标准 SQL 语法，灵活且易理解
- 配置优先级明确，支持不同环境

### Decision 6: 数据库验证失败的处理
**决策**：数据库验证失败时：
- 记录查询 SQL、查询结果、预期值、实际值
- 触发页面内容采集（如 Decision 1）
- 在 Cursor 分析工件中包含数据库验证失败信息（SQL、结果、预期/实际）
- 测试步骤标记为失败，继续后续步骤或停止（取决于测试计划配置）

**原因**：数据库验证失败与页面断言失败同等重要，需要完整的上下文供 Cursor 分析。

## Risks / Trade-offs

- **DOM 片段过大**：对复杂页面可能截断后仍较长。缓解：对 `outerHTML` 设硬上限并注明截断；可选只保留失败选择器对应节点。
- **敏感信息**：页面可能含 token、手机号等。缓解：不在设计里做自动脱敏，仅在文档中建议不在测试环境使用真实敏感数据；若后续需要可再加脱敏规则。
- **数据库连接失败**：测试环境数据库可能不可用或配置错误。缓解：数据库验证步骤失败时记录错误但不阻塞其他步骤；支持跳过数据库验证的配置选项。
- **数据库查询性能**：复杂查询可能较慢。缓解：建议测试计划中使用简单查询（如 COUNT、单行查询）；可设置查询超时（如 5 秒）。
- **数据库状态污染**：测试可能修改数据库状态，影响后续测试。缓解：建议在测试计划中明确测试数据清理策略；不在本设计中强制实现自动清理。

### Decision 7: Task 分解与用例状态持久化
**决策**：
- **Task 结构**：测试计划支持可选的 `tasks` 字段，每个 task 包含 `id`, `name`, `description`, `test_cases`（用例 ID 列表）。用例仍可直接在 `test_cases` 中定义，task 仅用于组织；若未定义 task，所有用例视为一个默认 task。
- **用例状态持久化**：执行器在执行用例后，将用例状态（passed/failed/skipped）、执行时间、错误信息（如有）保存到状态文件（如 `<plan_file>.status.json`，与计划文件同目录）。状态文件格式：`{"case_id": {"status": "passed", "executed_at": "ISO timestamp", "error": null}, ...}`。
- **跳过已成功用例**：执行器启动时加载状态文件（如存在），对于状态为 `passed` 的用例，除非用户指定 `--force` 或 `--rerun`，否则跳过执行并标记为 `skipped`（在结果中记录 `skipped_reason: "previously_passed"`）。
- **Task 级执行**：支持通过命令行参数指定仅执行某个 task（如 `--task task_1`），此时仅执行该 task 包含的用例；若未指定，执行所有 task 或所有用例。

**原因**：
- 大型测试计划可分解为多个 task，便于分阶段执行和进度跟踪
- 用例状态持久化避免重复执行已通过的用例，节省时间
- 支持强制重新测试（`--force`）或仅重新测试失败的用例（`--rerun-failed`）
- 状态文件与计划文件分离，不影响计划文件本身

### Decision 8: 状态文件格式与位置
**决策**：
- **位置**：默认与测试计划文件同目录，文件名 `<plan_basename>.status.json`（如 `plan.json` → `plan.status.json`）
- **格式**：
  ```json
  {
    "case_id_1": {
      "status": "passed",
      "executed_at": "2026-01-28T12:00:00",
      "error": null,
      "execution_time_seconds": 5.2
    },
    "case_id_2": {
      "status": "failed",
      "executed_at": "2026-01-28T12:05:00",
      "error": "Step 3 failed: Element not found",
      "execution_time_seconds": 3.1
    }
  }
  ```
- **更新时机**：用例执行完成后立即更新状态文件（追加或覆盖对应用例的状态）
- **清理**：用户可通过 `--force` 重置所有状态，或手动删除状态文件

**原因**：简单、可读、易于脚本处理；与计划文件分离避免污染计划文件；支持增量更新。

## Open Questions

- 是否需要在 SKILL 中增加「一键将最近一次 Cursor 分析工件粘贴到 Cursor」的示例命令（如 `cat ... | pbcopy`）？当前决策：可在 SKILL 中写使用说明与示例，不强制实现脚本。
- Task 是否需要支持依赖关系（如 task_2 依赖 task_1）？当前决策：暂不支持，task 仅用于组织用例，按顺序执行。

# Design: 专业 Skill Creator 工具

## Context

当前心域系统的技能创建主要通过简单的表单完成，缺乏专业指导和验证。Claude 官方的 Skill Creator 提供了以下核心能力：

1. **结构化格式**：基于 SKILL.md 文件（YAML 前置元数据 + Markdown 指令）
2. **设计原则**：
   - 简洁优先：只添加 Claude 本身不具备的知识
   - 自由度匹配：根据任务复杂度选择指令级别
   - 模块化设计：每个 Skill 是自包含的可复用单元
3. **验证规则**：
   - 名称格式：1-64字符，小写字母数字+单连字符（`^[a-z0-9]+(-[a-z0-9]+)*$`）
   - 描述长度：1-1024字符
   - 必需字段：name、description
4. **元数据支持**：license、compatibility、metadata 等可选字段

我们需要构建一个类似的工具，但将生成的技能存储到数据库而非文件系统。

## Goals

### Goals
1. **提供专业的技能创建工具** - 参考 Claude 官方规范，提供结构化的创建流程
2. **实现质量验证机制** - 自动验证技能名称、描述、元数据格式
3. **支持模板化创建** - 提供常用技能类型模板，加速创建过程
4. **增强技能元数据** - 支持完整的 Claude Skills 元数据字段
5. **改善技能描述质量** - 通过引导和验证确保描述科学、专业

### Non-Goals
- **文件系统存储** - 技能仍然存储在数据库中，不采用文件系统方式
- **技能市场/分享** - 暂不支持技能的市场化分享功能
- **版本控制系统集成** - 暂不集成 Git 等版本控制系统
- **Function Calling 支持** - 完全移除 Function Calling，改用 MCP 协议

## Decisions

### Decision 1: 技能结构设计
**采用 Claude Skills 规范结构**：
- **Level 1 (元数据)**：存储在 `skill_definitions` 表，包括 name、description、license、compatibility 等
- **Level 2 (指令)**：存储在 `skill_instructions` 表，支持多层级指令
- **Level 3 (资源)**：存储在 `skill_resources` 表，支持脚本、参考文档等

**理由**：
- 与 Claude 官方规范对齐，便于后续集成和迁移
- 数据库存储便于查询、管理和权限控制
- 支持版本管理和审计追踪

### Decision 2: 创建流程设计
**采用分步骤向导式创建**：
1. **基础信息**：技能ID、名称、描述、分类
2. **元数据配置**：许可证、兼容性、版本信息
3. **指令编写**：Markdown 格式的指令内容
4. **MCP 工具配置**：选择可用的 MCP 工具，配置工具参数
5. **执行配置**：执行类型、配置参数
6. **资源管理**：可选的脚本、参考文档
7. **预览与验证**：最终预览和格式验证

**理由**：
- 分步骤降低认知负担，提高创建质量
- 每步都有验证，及早发现问题
- 支持保存草稿，允许分多次完成
- 使用 MCP 工具而非 Function Calling，更标准化

### Decision 5: MCP 工具集成
**技能使用 MCP 协议调用工具**：
- **移除 Function Calling**：完全移除 `function_schema` 字段和相关支持
- **MCP 工具选择**：从系统中已配置且启用的 MCP 服务器中选择可用工具
- **工具验证**：创建技能时验证所选 MCP 工具是否可用，不可用的工具不能保存
- **工具参数配置**：支持配置 MCP 工具的参数映射和默认值

**理由**：
- MCP 是更标准的工具调用协议
- 与系统现有的 MCP 基础设施集成
- 确保工具可用性，避免运行时错误

### Decision 6: 返回合理性验证
**技能必须返回实际执行结果**：
- **禁止返回 FunctionCall 格式**：技能执行后必须返回实际结果，不能返回 FunctionCall 标记
- **结果验证**：验证技能返回的内容是否为有效的执行结果
- **降级方案**：如果 MCP 工具不可用，通过自然语言描述让大模型执行任务

**理由**：
- 确保用户体验，技能应返回可直接使用的信息
- 避免暴露内部实现细节（FunctionCall 格式）
- 提供灵活的降级方案，确保技能可用性

### Decision 3: 验证机制
**实现多层级验证**：
- **格式验证**：技能ID格式、描述长度、JSON Schema 格式
- **内容验证**：描述质量评分、关键词检查、完整性检查
- **业务验证**：技能ID唯一性、依赖关系检查

**理由**：
- 确保技能符合 Claude 规范
- 提高技能描述的科学性和专业性
- 减少错误和返工

### Decision 4: 模板系统
**提供分类模板库**：
- 按技能分类提供模板（如 UTILITY、HEALTHCARE、EDUCATION 等）
- 每个模板包含预填充的元数据、指令结构、MCP 工具配置示例
- 支持自定义模板保存和复用

**理由**：
- 加速常见技能类型的创建
- 确保同类技能的结构一致性
- 降低学习成本

## Risks / Trade-offs

### Risk 1: 数据库结构扩展
**风险**：扩展 `skill_definitions` 表可能影响现有代码
**缓解**：
- 新增字段设为可选，保持向后兼容
- 使用 Flyway 迁移脚本，支持回滚
- 充分测试现有功能不受影响

### Risk 2: 验证规则过于严格
**风险**：严格的验证可能阻碍快速创建
**缓解**：
- 提供警告和错误两种级别
- 允许保存草稿，稍后完善
- 提供验证规则的详细说明

### Risk 3: 与现有系统集成
**风险**：新工具可能与现有技能管理界面冲突
**缓解**：
- 新工具作为独立模块，不影响现有功能
- 提供两种创建方式：简单表单（现有）和专业创建器（新增）
- 统一的数据模型，确保兼容性

## Migration Plan

### Phase 1: 数据库扩展
1. 创建 Flyway 迁移脚本，添加新字段到 `skill_definitions` 表
2. 字段包括：`license`、`compatibility`、`metadata`（JSON）、`skill_content`（TEXT，存储完整 Markdown）
3. 验证现有数据不受影响

### Phase 2: 后端 API 开发
1. 创建 Skill Creator Service，实现创建、验证、模板管理
2. 扩展 Admin Skill Controller，添加创建器相关接口
3. 实现验证引擎，检查格式和内容质量

### Phase 3: 前端界面开发
1. 创建 Skill Creator 组件，实现分步骤向导
2. 集成验证反馈和错误提示
3. 实现模板选择和预览功能

### Phase 4: 测试与优化
1. 创建测试技能，验证完整流程
2. 性能测试和优化
3. 用户反馈收集和迭代

## Open Questions

1. **技能内容存储方式**：是否将完整的 SKILL.md 内容存储为单个字段，还是拆分为多个字段？
   - **建议**：存储为单个 `skill_content` TEXT 字段，便于导出和迁移

2. **模板管理**：模板是否也需要存储在数据库中？
   - **建议**：初始版本使用代码中硬编码的模板，后续可扩展为数据库存储

3. **技能导入导出**：是否支持从 SKILL.md 文件导入，或导出为 SKILL.md 格式？
   - **建议**：Phase 1 暂不支持，后续版本可添加

4. **MCP 工具不可用时的处理**：如果选择的 MCP 工具在运行时不可用，如何处理？
   - **建议**：使用自然语言描述作为降级方案，让大模型根据描述执行任务

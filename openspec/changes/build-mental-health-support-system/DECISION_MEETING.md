# 决策会议：心理健康支持系统与心理导师系统整合策略

**会议日期**: 2025-01-09  
**会议目标**: 确定心理健康支持系统与现有心理导师系统的整合策略  
**决策者**: 开发团队

---

## 一、现状分析

### 1.1 心理导师系统（MindScape AI Clinic）

**位置**: `aistudio/backend`  
**端口**: 8082  
**状态**: ✅ 已实现并运行

**核心能力**:
- ✅ 5种治疗流派：CBT、DBT、ACT、心理动力学、人本主义
- ✅ 5个专业治疗师角色（Dr. Cognos、Sage Harmony等）
- ✅ 深度知识库（生成1000+字专业学术解析）
- ✅ 17个临床案例库
- ✅ 智能会话管理（诊前评估、实时对话、会话总结）
- ✅ 心理学事实提取（情绪模式、认知扭曲、应对策略）
- ✅ 疗法智能推荐
- ✅ 记忆系统（Redis短期记忆 + MongoDB长期记忆）

**架构特点**:
- 独立Spring Boot服务
- 完整的RESTful API
- 独立的数据库（MongoDB）
- 独立的会话管理

### 1.2 提案：心理健康支持系统

**位置**: `main/backend`（计划）  
**目标**: 在main项目中构建专门的心理健康支持场景

**核心能力**（计划）:
- 专门的心理健康场景（青少年/成人模式）
- 多个专业心理健康角色（与心理导师系统重叠）
- 心理疗愈知识库（RAG）
- 多角色协同机制
- 危机识别和处理

### 1.3 现有main项目心理健康相关能力

**已有角色**:
- 心小安（心理健康守护者）：8个心理健康技能
- 心小暖（情绪陪伴师）：8个情绪陪伴技能

**已有基础设施**:
- ✅ 多智能体协作框架（`multiagent`）
- ✅ 场景系统
- ✅ 角色系统
- ✅ 向量检索和RAG能力（Context Engine v3）
- ✅ 记忆系统（Redis + MongoDB）

## 二、问题分析

### 2.1 核心问题

1. **角色重叠**: 提案要创建的角色与心理导师系统的治疗师角色高度重叠
2. **知识库重复**: 心理导师系统已有知识库，提案要新建知识库
3. **架构分离**: 心理导师系统在aistudio（独立服务），提案在main项目
4. **功能定位不清**: 两个系统的使用场景和定位不明确

### 2.2 关键决策点

- **决策1**: 两个系统的关系是什么？（集成/差异化/整合）
- **决策2**: 知识库如何建设？（复用/新建/分工）
- **决策3**: 角色如何定位？（复用/新建/差异化）
- **决策4**: 架构如何组织？（统一/独立/混合）

## 三、整合策略选项

### 选项A：API集成模式（推荐⭐⭐⭐⭐⭐）

**核心思路**: 保持心理导师系统独立，通过API集成到main项目的多智能体框架中

**3. 多智能体协作**
- 心小安/心小暖（现有角色）继续使用
- 心理导师系统的治疗师通过Agent包装器参与协作
- 新增角色：危机干预专家、青少年心理支持师

#### 优势

✅ **保持系统独立性**: 心理导师系统保持独立，便于维护和升级  
✅ **避免重复建设**: 复用心理导师系统的知识和角色  
✅ **灵活扩展**: main项目可以扩展新角色和新知识  
✅ **架构清晰**: 职责分离，main项目负责场景和协作，aistudio负责专业治疗  
✅ **渐进式实施**: 可以逐步集成，风险低

#### 劣势

⚠️ **网络依赖**: 需要HTTP调用，有网络延迟  
⚠️ **数据同步**: 需要处理数据一致性问题  
⚠️ **错误处理**: 需要处理服务不可用的情况

#### 实施步骤

1. **Phase 1**: 创建Agent包装器，将心理导师系统的治疗师包装为Agent
2. **Phase 2**: 实现知识库API集成，复用心理导师系统的知识库
3. **Phase 3**: 扩展知识库，添加青少年内容、危机处理等
4. **Phase 4**: 实现多智能体协作，整合现有角色和新角色
5. **Phase 5**: 创建心理健康场景，整合所有能力

**核心思路**: 将心理导师系统的功能迁移到main项目，统一管理

```
│  │  │  - 心小安/心小暖（现有）            │  │  │
│  │  │  - CBT/DBT/ACT等治疗师（迁移）      │  │  │
│  │  │  - 危机干预专家（新建）             │  │  │
│  │  │  - 青少年心理支持师（新建）          │  │  │
│  │  └────────────────────────────────────┘  │  │
│  │  ┌────────────────────────────────────┐  │  │
│  │  │  统一心理健康知识库（RAG）           │  │  │
│  │  │  - 心理导师系统知识库（迁移）        │  │  │
│  │  │  - 扩展：青少年内容、危机处理等      │  │  │
│  │  └────────────────────────────────────┘  │  │
│  └──────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

#### 实现方案

- 将心理导师系统的代码迁移到main项目
- 将知识库数据迁移到main项目的数据库
- 统一在main项目中管理所有心理健康相关功能

#### 优势

✅ **统一管理**: 所有功能在一个项目中，便于管理  
✅ **性能更好**: 无网络调用，响应更快  
✅ **数据一致**: 统一数据库，数据一致性好

#### 劣势

⚠️ **迁移成本高**: 需要大量代码迁移工作  
⚠️ **风险大**: 可能影响现有心理导师系统的稳定性  
⚠️ **失去独立性**: 心理导师系统失去独立部署的能力

### 选项C：差异化定位模式

**核心思路**: 明确两个系统的不同定位，避免功能重叠

#### 系统定位

| 系统 | 定位 | 使用场景 | 角色类型 | 知识库 |
|------|------|---------|---------|--------|
| **心理导师系统** | 专业治疗 | 结构化治疗会话、深度治疗 | 专业治疗师（5种流派） | 深度学术知识库 |
| **心理健康支持系统** | 日常支持 | 场景化支持、多角色协同 | 支持型角色（心小安/心小暖 + 新建角色） | 日常支持知识库 |

#### 实现方案

- 心理导师系统：保持独立，专注于专业治疗
- 心理健康支持系统：在main项目中新建，专注于日常支持和场景化体验
- 两个系统通过API互相调用，但不共享角色

#### 优势

✅ **定位清晰**: 两个系统有明确的差异化定位  
✅ **避免冲突**: 不会产生角色和功能重叠

#### 劣势

⚠️ **可能重复**: 知识库可能仍有重复内容  
⚠️ **用户体验**: 用户需要在两个系统间切换

## 四、推荐方案：选项A（API集成模式）

### 4.1 推荐理由

1. **最大化复用**: 充分利用现有心理导师系统的资源和能力
2. **架构合理**: 符合项目间通过HTTP通信的架构原则
3. **风险可控**: 渐进式实施，不影响现有系统
4. **扩展灵活**: main项目可以灵活扩展新功能
5. **维护简单**: 各系统保持独立，便于维护

### 4.2 关键设计决策

#### 决策1: Agent包装器设计

**决策**: 创建`PsychologyMentorAgentWrapper`，将心理导师系统的治疗师包装为Agent

**实现**:
```java
@Component
public class PsychologyMentorAgentWrapper extends BaseAgent {
    private final PsychologyMentorApiClient apiClient;
    private final String therapyMethodId; // "cbt", "dbt", etc.
    
    @Override
    protected AgentResult doExecute(String task, Map<String, Object> context) {
        // 1. 调用心理导师系统API创建会话
        String sessionId = apiClient.startSession(userId, therapyMethodId, context);
        
        // 2. 发送消息
        String response = apiClient.sendMessage(sessionId, task);
        
        // 3. 返回结果
        return AgentResult.success(response);
    }
}
```

#### 决策2: 知识库集成策略

**决策**: 通过API复用心理导师系统的知识库，在main项目中扩展新内容

**实现**:
```java
@Service
public class MentalHealthKnowledgeBaseService {
    private final PsychologyMentorApiClient apiClient;
    private final VectorSearchService vectorSearchService; // 本地扩展知识库
    
    public List<KnowledgeEntry> search(String query, String population) {
        // 1. 从心理导师系统获取知识（通过API）
        List<KnowledgeEntry> mentorKnowledge = apiClient.searchKnowledge(query);
        
        // 2. 从本地扩展知识库获取知识（RAG）
        List<KnowledgeEntry> localKnowledge = vectorSearchService.search(query, population);
        
        // 3. 合并和排序
        return mergeAndRank(mentorKnowledge, localKnowledge);
    }
}
```

#### 决策3: 角色定位和分工

**决策**: 明确各角色的定位和使用场景

| 角色 | 来源 | 定位 | 使用场景 |
|------|------|------|---------|
| 心小安/心小暖 | main项目（现有） | 日常心理健康支持 | 日常对话、基础支持 |
| CBT/DBT/ACT等治疗师 | 心理导师系统（包装） | 专业治疗 | 需要专业治疗时 |
| 危机干预专家 | main项目（新建） | 危机处理 | 识别到危机时 |
| 青少年心理支持师 | main项目（新建） | 青少年专门支持 | 青少年模式 |

#### 决策4: 多智能体协作流程

**决策**: 实现智能路由，根据用户需求选择合适的角色组合

**流程**:
1. 用户请求 → `MentalHealthRouter`分析需求
2. 路由决策：
   - 日常支持 → 心小安/心小暖
   - 专业治疗 → 心理导师系统治疗师（通过Agent包装器）
   - 危机情况 → 危机干预专家 + 相关治疗师
   - 青少年需求 → 青少年心理支持师 + 相关角色
3. `MentalHealthOrchestrator`协调多角色协作
4. 整合结果返回用户

## 五、决策记录

# Design: Mental Health Support System

## Context

当前系统已有：
1. **多智能体协作基础设施**：基于 AgentScope 的多智能体协作框架，支持智能体注册、路由、编排等能力
2. **场景系统**：支持创建和管理场景（时代切片），场景包含角色、剧情等
3. **角色系统**：支持创建角色，角色具备技能和能力
4. **现有心理健康角色**：
   - 心小安（心理健康守护者）：8个心理健康技能
   - 心小暖（情绪陪伴师）：8个情绪陪伴技能
   - 心理导师系统：支持5种治疗流派（CBT、DBT、心理动力学、ACT、人本主义）
5. **知识检索能力**：Context Engine v3 支持向量检索和RAG能力
6. **记忆系统**：支持短期记忆（Redis）和长期记忆（MongoDB）

**用户需求**：
- 关注青少年和成人的心理健康
- 为受心理问题困扰的人提供专业支持
- 需要多个专业角色协同工作
- 需要专业知识库支持

## Goals / Non-Goals

### Goals

**心理健康场景**：
- 创建专门的心理健康支持场景，提供安全、私密、专业的支持环境
- 支持青少年和成人两种模式，针对不同人群提供差异化体验
- 场景设计考虑心理健康支持的特殊需求（隐私、安全、专业性）

**专业化角色**：
- 创建多个具备专业心理治疗知识和技能的角色
- 每个角色具备特定的治疗流派专长和核心能力
- 角色能够识别危机情况，进行风险评估，提供专业干预
- 支持多角色协同，共同为用户提供综合支持

**知识库系统**：
- 构建心理治疗、心理疗愈相关的专业知识库
- 支持向量化存储和语义检索（RAG）
- 知识库内容涵盖心理治疗理论、干预技术、案例库、量表工具、危机处理流程等
- 为心理健康角色提供实时、准确的专业知识支持

**多角色协同**：
- 基于现有的多智能体协作框架，实现心理健康角色的协同工作
- 支持角色间的专业咨询、转介、会诊等协作模式
- 实现智能任务路由，根据用户需求自动选择合适的角色组合

### Non-Goals

- 不替代专业心理治疗师或精神科医生（系统提供支持，但不进行诊断）
- 不实现完整的电子病历系统（初期版本）
- 不实现跨机构的角色协作（初期版本仅限系统内）
- 不实现复杂的心理评估和诊断功能（初期版本聚焦支持而非诊断）
- 不实现实时视频或语音治疗（初期版本聚焦文本交互）

## Decisions

### Decision 1: 基于现有多智能体框架扩展
**What**: 复用现有的多智能体协作基础设施，在此基础上构建心理健康专业化扩展

**Rationale**:
- 系统已有成熟的多智能体协作框架（`multiagent`），无需重复建设
- 心理健康角色作为新的应用场景，使用现有基础设施可以快速实现
- 保持架构一致性，降低维护成本

**Alternatives considered**:
- 独立构建心理健康多智能体系统：开发成本高，与现有系统割裂
- 仅使用单角色模式：无法满足复杂心理健康问题的多专业协同需求

**Implementation**:
- 在 `main/backend/src/main/java/com/heartsphere/character/multiagent/mentalhealth/` 中实现心理健康角色协作
- 使用现有的 `CollaborationOrchestrator` 和 `AgentRouter` 接口
- 实现 `MentalHealthOrchestrator` 和 `MentalHealthRouter` 作为应用场景层

### Decision 2: 知识库建设策略（复用+扩展）
**What**: 通过API复用心理导师系统的知识库，在main项目中扩展新内容，使用RAG技术进行语义检索

**Rationale**:
- 心理导师系统已有深度知识库和17个临床案例，避免重复建设
- 通过API集成，保持系统独立性
- 在main项目中扩展青少年相关内容、危机处理流程等新知识
- 使用Context Engine v3的向量检索和RAG能力进行语义检索

**Alternatives considered**:
- 完全新建知识库：开发成本高，可能重复建设
- 完全复用心理导师系统：无法扩展新内容，灵活性差
- 独立构建向量数据库：开发成本高，维护复杂

**Implementation**:
- **API集成**: 通过`PsychologyMentorApiClient`调用心理导师系统的知识库API
- **本地扩展**: 在main项目中构建扩展知识库（青少年内容、危机处理等）
  - 使用现有的 `VectorSearchService` 进行向量检索
  - 知识库内容存储在 MongoDB，向量存储在向量数据库
- **知识库服务**: 在 `main/backend/src/main/java/com/heartsphere/knowledge/mentalhealth/` 中实现
  - `MentalHealthKnowledgeBaseService`: 知识库服务接口
  - `MentalHealthRAGService`: RAG检索服务，合并API获取的知识和本地扩展知识
  - 实现知识库合并和排序逻辑

### Decision 3: 场景系统扩展而非新建
**What**: 在现有场景系统基础上扩展，支持心理健康场景的特殊需求

**Rationale**:
- 系统已有场景系统，支持创建和管理场景
- 心理健康场景是场景系统的一个特殊应用，而非独立系统
- 保持系统架构一致性

**Alternatives considered**:
- 独立构建心理健康场景系统：与现有场景系统割裂，增加维护成本
- 不创建专门场景：无法提供专业化的心理健康支持环境

**Implementation**:
- 在场景系统中添加心理健康场景类型
- 场景包含心理健康特定的配置（隐私设置、安全设置、角色配置等）
- 前端提供专门的心理健康场景界面

### Decision 4: 角色技能与知识库结合
**What**: 心理健康角色的技能执行时，通过RAG检索专业知识库获取支持

**Rationale**:
- 角色技能需要专业知识支持，知识库提供准确、权威的知识
- RAG技术可以确保角色回答的专业性和准确性
- 知识库可以持续更新，提升角色能力

**Alternatives considered**:
- 仅依赖角色预设知识：知识有限，无法应对复杂情况
- 仅依赖LLM生成：可能产生不准确或不符合专业标准的内容

**Implementation**:
- 角色技能执行时，先通过RAG检索相关知识
- 将检索到的知识作为上下文提供给LLM
- LLM基于专业知识和用户情况生成回答

### Decision 5: 分人群设计
**What**: 场景和角色设计考虑青少年和成人的不同需求，提供差异化支持

**Rationale**:
- 青少年和成人的心理特点、需求、沟通方式不同
- 需要针对性的支持方案和交互方式
- 符合用户需求中的"关注青少年以及成人等不同人群"

**Alternatives considered**:
- 统一设计：无法满足不同人群的差异化需求
- 完全独立设计：开发成本高，维护复杂

**Implementation**:
- 场景支持"青少年模式"和"成人模式"切换
- 角色根据用户人群调整沟通方式和干预策略
- 知识库内容标注适用人群（青少年/成人/通用）

### Decision 6: 与心理导师系统的关系（API集成模式）
**What**: 通过API集成模式，将心理导师系统的治疗师和知识库集成到main项目的多智能体框架中

**Rationale**:
- 心理导师系统（aistudio/backend）已有完整的5种治疗流派、深度知识库和17个临床案例
- 避免重复建设，最大化复用现有资源
- 保持系统独立性，符合项目间通过HTTP通信的架构原则
- 渐进式实施，风险可控，不影响现有系统

**Alternatives considered**:
- **功能迁移模式**: 将心理导师系统迁移到main项目
  - 优势：统一管理，性能更好
  - 劣势：迁移成本高，风险大，失去独立性
- **差异化定位模式**: 两个系统完全独立，避免功能重叠
  - 优势：定位清晰，避免冲突
  - 劣势：可能重复，用户体验割裂

**Implementation**:
- **Agent包装器**: 创建`PsychologyMentorAgentWrapper`，将心理导师系统的治疗师包装为Agent
  - 通过HTTP API调用心理导师系统的会话管理接口
  - 将5种治疗流派（CBT、DBT、ACT、心理动力学、人本主义）的治疗师包装为Agent
  - 注册到main项目的多智能体系统中
- **知识库集成**: 通过API复用心理导师系统的知识库，在main项目中扩展新内容
  - 通过API调用心理导师系统的知识库接口
  - 在main项目中扩展：青少年相关内容、危机处理流程、日常支持知识等
  - 实现知识库合并和排序逻辑
- **角色定位和分工**:
  - 心小安/心小暖（现有）：日常心理健康支持
  - 心理导师系统治疗师（包装）：专业治疗场景
  - 危机干预专家（新建）：危机处理
  - 青少年心理支持师（新建）：青少年专门支持
- **多智能体协作**: 通过`MentalHealthRouter`和`MentalHealthOrchestrator`实现智能路由和协作
  - 根据用户需求智能选择角色组合
  - 支持角色间的咨询、转介、会诊等协作模式

**参考文档**: 详细决策分析见 `DECISION_MEETING.md`

## Risks / Trade-offs

### Risk 1: 专业知识准确性
**风险**: 知识库内容不准确或过时，可能导致角色提供错误建议

**缓解措施**:
- 知识库内容来源权威（心理学教材、专业期刊、治疗手册等）
- 建立内容审核机制，确保知识准确性
- 角色回答时明确说明这是支持而非诊断
- 设置免责声明，建议严重情况寻求专业帮助

### Risk 2: 危机识别和处理
**风险**: 系统可能无法及时识别或处理心理危机情况

**缓解措施**:
- 角色具备危机识别能力，能够识别自杀、自伤等高风险信号
- 建立危机处理流程，包括风险评估、紧急转介等
- 提供紧急求助渠道和资源
- 定期更新危机处理知识库

### Risk 3: 隐私和安全
**风险**: 心理健康信息高度敏感，需要严格的隐私保护

**缓解措施**:
- 场景支持隐私模式，数据加密存储
- 用户数据隔离，确保隐私安全
- 符合相关隐私法规要求
- 提供数据删除和导出功能

### Risk 4: 知识库建设成本
**风险**: 构建高质量的心理健康知识库需要大量专业内容

**缓解措施**:
- 分阶段建设，先构建核心知识，逐步扩展
- 建立内容贡献机制，支持专业内容导入
- 利用现有资源（心理导师系统的知识、公开的专业资料等）
- 考虑与专业机构合作获取权威内容

## Migration Plan

### Phase 1: 基础设施准备（1-2周）
1. 扩展场景系统，支持心理健康场景类型
2. 准备知识库存储和向量化基础设施
3. 扩展多智能体协作框架，支持心理健康角色

### Phase 2: 知识库建设（2-3周）
1. 收集和整理心理健康专业知识内容
2. 实现知识库存储和向量化
3. 实现RAG检索服务
4. 建立知识库管理和更新机制

### Phase 3: 角色开发（2-3周）
1. 设计和实现多个专业心理健康角色
2. 实现角色技能和知识库集成
3. 实现角色间的协作机制
4. 实现危机识别和处理能力

### Phase 4: 场景和前端（1-2周）
1. 实现心理健康场景后端逻辑
2. 实现前端场景界面
3. 实现角色交互界面
4. 实现知识库检索界面（可选）

### Phase 5: 测试和优化（1-2周）
1. 功能测试
2. 安全性测试
3. 性能优化
4. 用户体验优化

## Open Questions

1. **知识库内容来源**：是否需要与专业机构合作获取权威内容？如何确保内容的准确性和时效性？
2. **危机处理流程**：系统识别到危机情况后，具体的处理流程是什么？是否需要与外部机构（如危机干预热线）集成？
3. **角色数量**：初期应该实现多少个专业角色？每个角色的专业深度如何平衡？
4. **青少年模式**：青少年模式是否需要家长或监护人参与？如何平衡隐私和支持？
5. **知识库更新**：知识库的更新频率和机制是什么？是否需要版本管理？
6. **API稳定性**：心理导师系统API的稳定性和版本兼容性如何保证？
7. **性能优化**：如何优化API调用的性能，减少网络延迟对用户体验的影响？

## Integration with Psychology Mentor System

### Architecture Overview

```
main项目（心理健康支持系统）
├── 心理健康场景
├── 多智能体协作框架
│   ├── 心小安/心小暖（现有角色）
│   ├── PsychologyMentorAgentWrapper（Agent包装器）
│   │   ├── CBT治疗师Agent
│   │   ├── DBT治疗师Agent
│   │   ├── ACT治疗师Agent
│   │   ├── 心理动力学治疗师Agent
│   │   └── 人本主义治疗师Agent
│   ├── 危机干预专家（新建）
│   └── 青少年心理支持师（新建）
└── 知识库服务
    ├── API集成（心理导师系统知识库）
    └── 本地扩展（青少年内容、危机处理等）
         │
         ▼ HTTP API
心理导师系统（aistudio/backend）
├── 5种治疗流派治疗师
├── 深度知识库
├── 17个临床案例
└── 会话管理
```

### Integration Points

1. **Agent包装器**: 将心理导师系统的治疗师包装为Agent，参与多智能体协作
2. **知识库API**: 通过API调用心理导师系统的知识库，获取专业治疗知识
3. **会话管理**: 通过API调用心理导师系统的会话管理，支持专业治疗会话

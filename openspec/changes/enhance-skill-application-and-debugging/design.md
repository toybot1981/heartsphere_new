# Design: 技能应用与调试体系

## Context

当前心域系统具有完整的技能定义框架（skill_definitions 表），支持多种执行类型（SCRIPT、API、GRAPH、DATABASE、RULE_BASED）。然而，在对话处理过程中，技能的选择、应用、执行的具体流程缺乏清晰的设计。

此外，当前系统的调试能力主要聚焦于记忆系统，对于技能应用的调试缺乏可见性。开发者难以理解为什么某个技能被激活、参数是什么、执行结果如何。

本设计旨在建立一套完整的技能应用引擎和调试体系。

**关键约束**：
- 技能应用不应阻塞 AI 响应生成（异步或通过评分快速决定）
- 调试信息应尽可能详细但不影响生产环境性能
- 技能应用与记忆系统应协同工作

## Goals

### Goals
1. **提供清晰的技能应用决策流程** - 使用评分机制和优先级排序，使技能选择可预测和可调试
2. **实现完整的技能执行追踪** - 从评估到完成的每个步骤都有记录，支持深度调试
3. **提高调试可见性** - 开发者能在聊天窗口中实时查看技能激活信息
4. **增强用户理解** - 用户知道 AI 为什么使用某个技能
5. **支持技能-记忆协同** - 技能应用能利用记忆系统的数据，且决策过程可溯源

### Non-Goals
- **实时技能执行优化** - 这是后续性能优化工作
- **多轮技能链执行** - 暂不支持一个技能的输出作为另一个技能的输入
- **技能学习/演化** - 技能定义保持静态（可通过 Admin 管理更新）
- **跨会话技能上下文** - 技能执行上下文仅在单个会话内维持

## Decisions

### Decision 1: 技能评分机制
**采用多维度评分模型**：
- **关键词匹配得分** (0-100): 基于技能自动触发关键词与用户消息的文本匹配
- **语义相似度得分** (0-100): 基于技能描述与用户意图的语义相似度（使用 embeddings 或 LLM）
- **上下文匹配得分** (0-100): 基于当前对话阶段、用户历史、角色状态等因素
- **内存触发得分** (0-100): 基于相关记忆/用户属性是否匹配技能条件

**综合得分** = 关键词权重 × 关键词得分 + 语义权重 × 语义得分 + 上下文权重 × 上下文得分 + 内存权重 × 内存得分

**权重配置**：
- 默认配置在 application.yml 中
- 可通过 Admin 接口调整，支持 A/B 测试

**阈值**：
- 仅当综合得分 > 设定阈值（默认 60 分）时，技能才被考虑应用
- 阈值可配置

**备选方案**：
- 模型驱动方案：直接使用 LLM 评估技能适用性（成本高、延迟高，保留作为可选项）
- 规则驱动方案：基于人工配置的规则评估（不够灵活）

**选择理由**：多维度评分方案在准确性、性能和可调试性之间取得良好平衡

---

### Decision 2: 技能执行优先级管理
**采用优先级队列模型**：
- 评估后的技能按综合得分排序
- 依次考虑应用，满足执行条件的第一个技能被选中应用
- 支持同时应用多个技能（通过配置控制），但按优先级串行执行以避免冲突

**应用条件检查**：
- 权限检查：用户是否有权限使用该技能
- 冷却时间检查：技能是否在冷却期内
- 日使用限制检查：当日使用次数是否超限
- 前置条件检查：技能定义中的任何前置条件（如需要特定角色状态）

**备选方案**：
- 并行评估 + 智能冲突解决：多个技能同时执行但通过协议管理互相影响（复杂度高）

**选择理由**：简单清晰，易于调试和控制

### Decision 3: 执行记录存储设计
**表结构**：`skill_execution_records`

```
id (PK)
conversation_id (FK)
skill_id (FK)
user_id (FK)
role_id (FK)

-- 评估阶段
evaluation_context (JSON) - 完整的评估上下文快照
evaluation_timestamp
keyword_matches (JSON) - 匹配的关键词列表
semantic_score (INT) - 0-100
context_score (INT) - 0-100
memory_score (INT) - 0-100
composite_score (INT) - 0-100
decision (ENUM: APPLIED/REJECTED)
rejection_reason (VARCHAR) - 如果被拒绝，原因是什么

-- 应用阶段
execution_parameters (JSON) - 使用的参数
execution_status (ENUM: PENDING/EXECUTING/COMPLETED/FAILED)
execution_timestamp
execution_duration_ms

-- 结果阶段
execution_result (JSON) - 执行结果
error_message (TEXT) - 如果失败
resource_usage (JSON) - CPU、内存使用情况（可选）

-- 关联
related_memory_ids (JSON) - 影响决策的 memory ID 列表
related_conversation_turn_id (FK) - 触发此技能的对话轮次
updated_at
created_at
```

**索引策略**：
- (conversation_id, created_at) - 快速查询某个对话的技能历史
- (skill_id, created_at) - 快速查询某个技能的使用历史
- (user_id, skill_id, created_at) - 查询用户使用特定技能的历史
- decision 字段单独索引 - 快速查询成功/失败的应用

**查询模式**：
- 获取某个对话的技能执行历史（用于调试面板）
- 获取某个用户/技能的使用统计
- 按技能名称或类别过滤
- 时间范围过滤

**备选方案**：
- 内存存储：只在会话期间保留执行记录（不能持久化，不利于分析）
- NoSQL 存储：使用 MongoDB 存储 JSON 数据（增加运维复杂度）

**选择理由**：关系型数据库提供好的查询灵活性和事务支持，JSON 字段足够存储复杂的上下文信息

---

### Decision 4: 技能-记忆关联追踪

**设计**：
- 在执行记录的 `related_memory_ids` 字段中存储影响决策的 memory ID 列表
- Memory 表中新增字段 `skill_influence_ids` (JSON)：存储受此记忆影响的技能执行 ID（可选，用于反向查询）
- 在调试面板中展示这种关联

**关联建立时机**：
- 技能评估时，记录哪些记忆被查询和使用
- 技能执行时，记录哪些记忆被修改或影响

**查询模式**：
- 给定技能执行记录 → 查询相关的 memories
- 给定 memory → 查询受其影响的技能执行记录

**备选方案**：
- 独立关联表：创建 skill_memory_correlations 表（更灵活但增加复杂度）

**选择理由**：在当前简单模型中，在 execution_records 中存储关联足够；未来如需更复杂的关联逻辑再迁移

### Decision 5: 调试面板架构

**前端组件结构**：
```
ChatWindow
├── ConversationArea
│   └── MessageList
├── DebugPanel (与记忆调试框并列)
│   ├── Tabs/Selector
│   │   ├── MemoryDebugTab
│   │   └── SkillDebugTab (新增)
│   └── SkillDebugPanel
│       ├── SkillActivationList
│       │   └── SkillActivationItem (可展开)
│       │       ├── SkillBasicInfo
│       │       ├── ActivationReason
│       │       ├── ExecutionStatus
│       │       └── DetailedInfo (展开时)
│       └── Filters & Controls
```

**数据流**：
- 后端通过 WebSocket 或轮询推送技能执行事件到前端
- 前端接收事件，更新调试面板显示
- 用户点击展开查看详情时，前端发送 API 请求获取完整执行记录

**后端服务层**：
- `SkillApplicationEngine` - 核心引擎，负责评估和应用
- `SkillExecutionRecordService` - 管理执行记录
- `SkillDebugController` - REST API for debugging queries
- `SkillDebugWebSocketHandler` - WebSocket 实时推送（可选，初期通过轮询）

**备选方案**：
- 完全前端评估模式：所有评估逻辑在前端执行（不安全，难以维护）
- Server-Sent Events：用于推送而非 WebSocket（更轻量级，但单向）

**选择理由**：WebSocket 提供真正的实时性，对于调试需求是最佳选择

## Risks / Trade-offs

### Risk 1: 性能开销
**风险**：执行记录、关联追踪会增加数据库写入和计算开销

**缓解**：
- 执行记录写入可以异步进行（使用消息队列或线程池）
- 评分计算可缓存部分结果（如用户偏好权重）
- 生产环境可通过配置降低记录详细程度

**监控**：监测数据库 I/O 和 AI 响应延迟，建立告警阈值

### Risk 2: 数据库表爆炸
**风险**：执行记录可能快速增长，导致表大小失控

**缓解**：
- 定期归档旧记录（>30 天）到归档表或数据仓库
- 设置记录保留策略（例如保留最近 90 天）
- 定期清理已归档数据

**索引管理**：定期重建索引以保持查询性能

### Risk 3: 调试信息泄露
**风险**：详细的技能执行记录和参数可能包含敏感信息

**缓解**：
- 调试面板仅对具有调试权限的用户显示
- 敏感参数（如 API Key）自动脱敏
- 调试信息仅在开发/测试环境完整显示，生产环境受限

### Risk 4: 技能优先级冲突
**风险**：多个技能有相似的适用性，选择顺序可能不够智能

**缓解**：
- 清晰的优先级配置和文档
- Admin 接口支持手动调整权重
- 通过 A/B 测试验证新的权重配置

### Risk 5: 集成复杂度
**风险**：需要修改 AI 响应处理流程，可能破坏现有功能

**缓解**：
- 技能应用引擎设计为插件式，可以启用/禁用
- 完整的单元测试覆盖
- 灰度发布策略，先在测试环境验证

## Migration Plan

### Phase 1: 后端基础实现（1-2 周）
1. 创建 `skill_execution_records` 表
2. 实现 `SkillApplicationEngine` 核心类
3. 实现 `SkillExecutionRecordService`
4. 编写详细的单元测试

**验证**：
- 能成功记录技能评估和应用过程
- 执行记录可正确查询和过滤

### Phase 2: 后端 API 和集成（1-2 周）
1. 创建 `SkillDebugController` 提供查询 API
2. 将 `SkillApplicationEngine` 集成到 AI 响应处理流程
3. 添加异步执行记录写入
4. 添加技能-记忆关联追踪

**验证**：
- API 能正确返回技能执行历史
- 实时对话过程中能记录所有技能应用
- 聊天记录包含技能元数据

### Phase 3: 前端调试面板（1-2 周）
1. 创建调试面板 UI 组件
2. 实现与后端 API 的连接
3. 实现技能激活事件的实时更新
4. 添加过滤和展开/折叠功能

**验证**：
- 调试面板能正确显示技能激活列表
- 可以展开查看详细信息
- 能正确链接到记忆调试框

### Phase 4: 用户界面集成（1 周）
1. 在 AI 响应中添加技能使用标记
2. 实现悬停/点击查看技能说明
3. 添加用户偏好设置（启用/禁用调试显示）
4. 实现内存-技能关联显示

**验证**：
- 用户能看到 AI 使用了哪些技能
- 用户能理解技能使用原因

### Phase 5: 优化和部署（1 周）
1. 性能优化和监控设置
2. 测试环境全流程测试
3. 灰度部署到生产环境
4. 性能监控和告警配置

**回滚计划**：
- 如果性能下降明显，可关闭异步记录功能
- 如果出现 Bug，可临时禁用技能应用引擎（退回到无技能应用模式）

## Open Questions

1. **评分权重初始值**：多维度评分中各维度的初始权重是多少？是否有已有的配置文档或经验数据？
   
2. **并发技能应用**：是否允许一次对话中同时应用多个技能，还是始终只应用一个？

3. **记忆集成范围**：在评估技能时，应该查询用户的哪些记忆类型（如用户偏好、历史行为、个人资料等）？

4. **性能指标**：系统期望的平均技能评估延迟是多少？这影响是否必须优化评分计算？

5. **归档策略**：执行记录的保留期是多少？是否需要实现自动归档？

6. **权限模型**：只有 Admin 能看调试面板，还是普通用户也可以启用更简化的版本？

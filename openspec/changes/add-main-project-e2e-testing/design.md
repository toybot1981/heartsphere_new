# Design: Main 项目端到端自动化测试架构

## Context

Main 项目（HeartSphere）是一个复杂的数字生命体交互系统，包含：
- **PC 版本**: 桌面端应用，功能完整
- **Mobile 版本**: 移动端应用，针对触摸优化
- **核心功能模块**:
  - 用户认证和登录
  - 场景管理（Era/World Scene）
  - 角色管理（Character）
  - AI 对话系统
  - 剧本系统（Script）
  - 信箱系统（Mailbox）
  - 心域连接（HeartConnect）
  - 用户设置
  - 其他辅助功能

当前项目已有 Jest 单元测试，但缺乏端到端测试覆盖。

## Goals

1. **全面功能覆盖**: 覆盖所有主要功能模块
2. **跨平台测试**: PC 和 Mobile 版本都要测试
3. **自动化执行**: 支持命令行执行和 CI/CD 集成
4. **详细报告**: 生成包含截图和详细信息的测试报告
5. **易于维护**: 测试代码结构清晰，易于扩展

## Non-Goals

- 不测试注册功能（用户明确要求）
- 不进行性能测试（专注于功能测试）
- 不进行安全测试（专注于功能验证）
- 不测试后端 API（专注于前端功能）

## Decisions

### 1. 测试框架选择

**决策**: 使用 Playwright

**理由**:
- 支持多浏览器（Chromium、Firefox、WebKit）
- 自动等待机制，减少 flaky 测试
- 内置截图和视频录制
- 强大的选择器和网络拦截能力
- 良好的 TypeScript 支持
- 活跃的社区和文档

**替代方案考虑**:
- Puppeteer: 功能类似，但只支持 Chromium
- Cypress: 更适合组件测试，端到端测试能力较弱
- Selenium: 较老的技术，配置复杂

### 2. 测试组织结构

**决策**: 按功能模块组织测试文件

**结构**:
```
e2e/
├── config/
│   ├── playwright.config.ts      # Playwright 配置
│   └── test-data.ts              # 测试数据（账号、测试数据等）
├── utils/
│   ├── helpers.ts                # 测试辅助函数
│   ├── page-objects.ts           # 页面对象模型
│   └── assertions.ts             # 自定义断言
├── tests/
│   ├── pc/
│   │   ├── login.spec.ts         # PC 登录测试
│   │   ├── scenario.spec.ts      # PC 场景管理测试
│   │   ├── character.spec.ts     # PC 角色管理测试
│   │   ├── chat.spec.ts          # PC 聊天测试
│   │   ├── script.spec.ts        # PC 剧本测试
│   │   ├── mailbox.spec.ts       # PC 信箱测试
│   │   ├── heartconnect.spec.ts  # PC 心域连接测试
│   │   └── settings.spec.ts      # PC 设置测试
│   └── mobile/
│       ├── login.spec.ts         # Mobile 登录测试
│       ├── scenario.spec.ts      # Mobile 场景管理测试
│       ├── character.spec.ts     # Mobile 角色管理测试
│       ├── chat.spec.ts          # Mobile 聊天测试
│       └── ...                   # 其他 Mobile 测试
├── reports/                      # 测试报告目录
└── screenshots/                  # 测试截图目录
```

**理由**:
- 清晰的功能模块划分
- 便于维护和扩展
- PC 和 Mobile 测试分离，便于独立执行

### 4. 测试报告格式

**决策**: 生成 HTML 和 JSON 格式报告

**HTML 报告**:
- 测试结果概览
- 每个测试用例的详细结果
- 失败测试的截图和错误信息
- 测试执行时间统计

**JSON 报告**:
- 机器可读的测试结果
- 支持 CI/CD 集成
- 支持测试结果分析工具

**理由**:
- HTML 报告便于人工查看
- JSON 报告便于自动化处理
- 支持多种使用场景

### 5. 测试执行策略

**决策**: 支持多种执行模式

**执行模式**:
1. **完整测试**: 执行所有测试用例
2. **PC 测试**: 只执行 PC 版本测试
3. **Mobile 测试**: 只执行 Mobile 版本测试
4. **单个模块测试**: 执行特定功能模块测试
5. **调试模式**: 使用 headed 模式，便于调试

**理由**:
- 灵活的执行选项
- 支持快速验证特定功能
- 便于调试和开发

## Risks / Trade-offs

### 风险 1: 测试稳定性
**风险**: 端到端测试可能因为网络延迟、异步操作等导致不稳定

**缓解措施**:
- 使用 Playwright 的自动等待机制
- 添加适当的等待和重试逻辑
- 使用稳定的选择器
- 定期维护和更新测试

### 风险 2: 测试执行时间
**风险**: 全面测试可能执行时间较长

**缓解措施**:
- 支持并行执行
- 支持选择性执行（PC 或 Mobile）
- 优化测试用例，减少不必要的等待
- 使用测试分组和标签

### 风险 3: 测试维护成本
**风险**: 前端 UI 变化可能导致测试失败

**缓解措施**:
- 使用页面对象模型（Page Object Model）
- 使用稳定的选择器（data-testid）
- 良好的测试代码结构
- 定期审查和更新测试

### 风险 4: 测试环境依赖
**风险**: 测试依赖开发服务器运行

**缓解措施**:
- 在测试脚本中检查服务器是否可用
- 提供清晰的错误提示
- 支持配置测试环境 URL
- 文档说明测试环境要求

## Open Questions

1. **测试数据清理**: 测试后是否需要清理测试数据？
   - **当前决策**: 测试数据可以保留，便于调试和验证

2. **测试并行度**: 是否支持并行执行多个测试？
   - **当前决策**: 支持，但需要确保测试之间不相互影响

3. **测试环境**: 是否需要独立的测试环境？
   - **当前决策**: 使用开发环境（localhost:3000），后续可扩展

4. **CI/CD 集成**: 是否需要集成到 CI/CD 流程？
   - **当前决策**: 先完成测试脚本，后续可集成

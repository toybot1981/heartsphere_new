# Design: 系统大重构 - 拆分为三个子项目

## Context

HeartSphere 是一个数字生命体交互系统，当前采用单体架构，包含：
- 客户端功能（PC Web、Mobile、微信小程序）
- 管理端功能（后台管理系统）
- Mentis 超级智能体功能

随着项目规模扩大，单体架构带来的问题日益突出，需要进行架构重构，将系统拆分为三个独立的子项目，同时建立共享代码库来管理公共代码。

## Goals / Non-Goals

### Goals

1. **项目拆分**：
   - 将客户端、管理端、Mentis 拆分为三个独立的子项目
   - 每个子项目包含独立的前端和后端
   - 支持独立开发、构建、测试和部署

2. **共享代码管理**：
   - 识别和提取三个子项目的公共代码
   - 建立共享代码库，统一管理公共代码
   - 定义清晰的共享代码使用规范

3. **依赖管理**：
   - 子项目通过依赖管理工具引用共享模块
   - 后端使用 Maven 多模块项目或 Git Submodule
   - 前端使用 npm/yarn workspace 或 Git Submodule

4. **向后兼容**：
   - 保持 API 接口兼容性
   - 数据库结构不变
   - 渐进式迁移，不影响现有功能

### Non-Goals

1. **不改变业务逻辑**：重构只涉及代码组织，不改变功能
2. **不拆分数据库**：三个子项目共享同一个数据库（可后续优化）
3. **不引入微服务架构**：本次重构只做项目拆分，不涉及服务拆分
4. **不改变技术栈**：保持现有的 Spring Boot、React、TypeScript 等技术栈

## Decisions

### Decision 1: 项目拆分粒度

**Chosen**: 按业务域拆分（客户端、管理端、Mentis），每个域包含完整的前后端

**Alternatives considered**:
1. 按技术层拆分（所有前端一个项目，所有后端一个项目）
   - Pros: 技术栈统一，便于管理
   - Cons: 业务耦合，难以独立部署和扩展

2. 按功能模块拆分（更细粒度）
   - Pros: 更灵活
   - Cons: 项目过多，管理复杂，过度设计

**Rationale**: 按业务域拆分既保持了业务内聚性，又实现了合理的解耦。三个子项目有明确的业务边界，可以独立开发和部署。

### Decision 2: 共享代码管理方式

**Chosen**: Git Submodule + 依赖管理工具

**具体方案**:
- **后端**: Maven 多模块项目，`shared-backend` 作为父模块的子模块
- **前端**: npm/yarn workspace，`shared-frontend` 作为 workspace 成员

**Alternatives considered**:
1. 独立的 npm/Maven 包发布到私有仓库
   - Pros: 版本管理清晰，依赖明确
   - Cons: 需要搭建私有仓库，开发时更新不便

2. 直接复制共享代码到各项目
   - Pros: 简单直接
   - Cons: 代码重复，维护困难

3. Git Submodule
   - Pros: 代码统一管理，版本控制清晰
   - Cons: 需要团队熟悉 Git Submodule 使用

**Rationale**: Git Submodule + 依赖管理工具既保证了代码的统一管理，又提供了良好的开发体验。开发时可以直接修改共享代码，发布时通过版本号管理。

### Decision 3: 共享代码识别原则

**Chosen**: 遵循以下原则识别共享代码

1. **必须共享**：
   - 数据库实体类（Entity）
   - 公共工具类（Utils）
   - 公共配置类（Config）
   - 公共异常类（Exception）
   - 公共类型定义（TypeScript types）
   - 公共 API 基础库

2. **可选共享**：
   - 公共 UI 组件（如果三个项目 UI 风格统一）
   - 公共业务逻辑（如果业务逻辑确实相同）

3. **不共享**：
   - 项目特定的业务逻辑
   - 项目特定的 UI 组件
   - 项目特定的配置

**Rationale**: 过度共享会导致耦合，共享不足会导致重复。遵循"最小共享原则"，只共享真正需要共享的代码。

### Decision 4: 数据库共享策略

**Chosen**: 三个子项目共享同一个数据库，通过表前缀或 schema 区分

**Alternatives considered**:
1. 每个子项目独立数据库
   - Pros: 完全隔离，互不影响
   - Cons: 数据同步复杂，跨项目查询困难

2. 共享数据库，独立 schema
   - Pros: 逻辑隔离，便于管理
   - Cons: 需要数据库支持 schema（MySQL 8.0+ 支持）

**Rationale**: 当前阶段保持数据库共享，简化数据管理。后续如果需要，可以迁移到独立 schema 或独立数据库。

### Decision 5: API 网关和路由

**Chosen**: 通过路径前缀区分不同子项目的 API

- 客户端 API: `/api/client/...`
- 管理端 API: `/api/admin/...`
- Mentis API: `/api/mentis/...`
- 共享 API: `/api/shared/...`（如认证、文件上传等）

**Alternatives considered**:
1. 独立域名和端口
   - Pros: 完全隔离
   - Cons: 需要额外的反向代理配置，CORS 配置复杂

2. 统一 API 网关
   - Pros: 统一入口，便于管理
   - Cons: 增加系统复杂度

**Rationale**: 路径前缀方案简单有效，不需要额外的基础设施，同时保持了清晰的 API 边界。

### Decision 6: 构建和部署策略

**Chosen**: 独立构建，可选联合部署

**构建策略**:
- 每个子项目独立构建（`mvn build`、`npm run build`）
- 共享模块作为依赖被引用
- 支持单独构建和联合构建

**部署策略**:
- 开发环境：可以联合部署（所有服务在一个进程）
- 生产环境：建议独立部署（不同端口或不同服务器）
- 支持 Docker 容器化部署

**Rationale**: 独立构建和部署提供了最大的灵活性，可以根据实际需求选择部署方式。

### 风险概览

本次重构共识别 **21 个风险**，其中：
- **高风险**: 7 个（必须重点关注）
- **中风险**: 9 个（需要关注）
- **低风险**: 5 个（需要监控）

### 高风险项（简要）

#### 风险 1: 迁移周期长，影响新功能开发

**风险**: 重构预计需要 11-17 周，可能影响新功能开发

**缓解措施**:
- 分阶段并行开发策略：迁移团队和主开发团队并行工作
- 资源分配策略：分配专门的迁移团队，不影响主开发团队
- 时间管理策略：压缩非关键阶段，优先完成核心迁移
- 功能冻结策略：在关键迁移阶段临时冻结部分非关键功能

**详细分析**: 参见 [RISK_ANALYSIS.md](./RISK_ANALYSIS.md#风险-1-迁移周期长影响新功能开发)

#### 风险 2: 代码重复和共享代码识别不准确

**风险**: 在拆分过程中可能产生代码重复，共享代码识别不准确

**缓解措施**:
- 使用代码分析工具（SonarQube、CodeClimate）检测重复代码
- 建立共享代码识别流程和决策机制
- 渐进式提取策略：先提取明确的，不确定的延后
- 代码审查机制：所有共享代码提取都需要审查

**详细分析**: 参见 [RISK_ANALYSIS.md](./RISK_ANALYSIS.md#风险-2-代码重复和共享代码识别不准确)

#### 风险 3: 依赖管理复杂，团队学习成本高

**风险**: Maven 多模块和 npm workspace 对团队可能是新技术

**缓解措施**:
- 技术培训：迁移前进行 2-3 次技术培训
- 工具和脚本支持：提供自动化脚本简化操作
- 文档和指南：编写详细的开发指南和 FAQ
- 渐进式引入：先在一个子项目中试点

**详细分析**: 参见 [RISK_ANALYSIS.md](./RISK_ANALYSIS.md#风险-3-依赖管理复杂团队学习成本高)

#### 风险 4: 数据库共享导致的数据隔离问题

**风险**: 三个子项目共享数据库，可能存在数据访问混乱

**缓解措施**:
- 数据访问控制：通过 API 路径和 Service 层权限检查
- 数据隔离策略：通过表前缀或 schema 区分
- 监控和审计：记录所有数据库操作日志
- 未来迁移准备：设计时考虑未来可能的数据库拆分

**详细分析**: 参见 [RISK_ANALYSIS.md](./RISK_ANALYSIS.md#风险-4-数据库共享导致的数据隔离问题)

#### 风险 5: API 路径变更导致的前端调用问题

**风险**: API 路径变更需要更新所有前端调用，可能遗漏

**缓解措施**:
- 自动化迁移工具：创建脚本自动更新前端 API 调用
- API 兼容层：在迁移过渡期保留旧 API 路径的兼容层
- 测试覆盖：编写完整的 API 集成测试和 E2E 测试
- 渐进式迁移：先迁移一个前端项目，验证方案

**详细分析**: 参见 [RISK_ANALYSIS.md](./RISK_ANALYSIS.md#风险-5-api-路径变更导致的前端调用问题)

#### 风险 6: 共享代码版本冲突

**风险**: 不同子项目可能需要不同版本的共享代码

**缓解措施**:
- 版本管理策略：使用语义化版本，共享代码使用独立版本号
- 向后兼容策略：优先保持向后兼容
- 依赖管理：各子项目明确指定共享代码版本
- 测试和验证：共享代码更新后，在所有子项目中运行测试

**详细分析**: 参见 [RISK_ANALYSIS.md](./RISK_ANALYSIS.md#风险-6-共享代码版本冲突)

#### 风险 7: 构建和部署流程复杂化

**风险**: 多个子项目需要独立的构建和部署流程

**缓解措施**:
- 统一构建脚本：创建统一的构建脚本，支持单独和联合构建
- CI/CD 流程优化：设计支持多项目的 CI/CD 流程
- 部署策略：支持独立部署和联合部署
- 容器化部署：使用 Docker 容器化各子项目

**详细分析**: 参见 [RISK_ANALYSIS.md](./RISK_ANALYSIS.md#风险-7-构建和部署流程复杂化)

### 中风险项（简要）

- **风险 8**: 测试策略不明确 - 建立测试策略文档，明确测试组织方式
- **风险 9**: 文档更新不及时 - 建立文档更新清单和审查机制
- **风险 10**: 团队协作流程变化 - 建立新的协作流程文档
- **风险 11**: 性能影响 - 进行性能测试和基准测试
- **风险 12**: 回滚困难 - 保留旧代码，建立详细的回滚计划

**详细分析**: 参见 [RISK_ANALYSIS.md](./RISK_ANALYSIS.md#中风险项需要关注)

### 风险缓解优先级

**优先级 1（立即实施）**:
1. 建立代码分析工具和流程
2. 创建技术培训计划
3. 建立 API 兼容层
4. 创建统一构建脚本

**优先级 2（迁移前完成）**:
1. 建立共享代码识别流程
2. 创建开发环境设置脚本
3. 建立测试策略
4. 创建部署脚本

**详细计划**: 参见 [RISK_MITIGATION_PLAN.md](./RISK_MITIGATION_PLAN.md)

## Migration Plan

### 阶段 1: 准备阶段（1-2 周）

1. **分析和规划**：
   - 分析现有代码结构
   - 识别共享代码
   - 制定详细的迁移计划

2. **创建新项目结构**：
   - 创建新的目录结构
   - 初始化各子项目
   - 创建共享代码库

3. **建立开发规范**：
   - 定义项目结构规范
   - 定义共享代码使用规范
   - 更新开发文档

### 阶段 2: 共享代码提取（2-3 周）

1. **提取共享后端代码**：
   - 提取公共 Entity、Utils、Config、Exception
   - 创建 `shared-backend` 模块
   - 更新各项目的依赖配置

2. **提取共享前端代码**：
   - 提取公共 types、utils、components
   - 创建 `shared-frontend` 模块
   - 更新各项目的依赖配置

3. **测试共享代码**：
   - 编写共享代码的单元测试
   - 验证各项目可以正常引用共享代码

### 阶段 3: 客户端项目迁移（3-4 周）

1. **迁移 PC Web 前端**：
   - 迁移到 `client/frontend-pc/`
   - 更新依赖和配置
   - 测试功能完整性

2. **迁移 Mobile 前端**：
   - 迁移到 `client/frontend-mobile/`
   - 更新依赖和配置
   - 测试功能完整性

3. **迁移小程序前端**：
   - 迁移到 `client/frontend-miniprogram/`
   - 更新依赖和配置
   - 测试功能完整性

4. **迁移客户端后端**：
   - 提取客户端相关的 controller、service
   - 迁移到 `client/backend/`
   - 更新 API 路径前缀为 `/api/client/`

### 阶段 4: 管理端项目迁移（2-3 周）

1. **迁移管理端前端**：
   - 迁移到 `admin/frontend/`
   - 更新依赖和配置
   - 测试功能完整性

2. **迁移管理端后端**：
   - 提取管理端相关的 controller、service
   - 迁移到 `admin/backend/`
   - 更新 API 路径前缀为 `/api/admin/`

### 阶段 5: Mentis 项目迁移（2-3 周）

1. **迁移 Mentis 前端**：
   - 迁移到 `mentis/frontend/`
   - 更新依赖和配置
   - 测试功能完整性

2. **迁移 Mentis 后端**：
   - Mentis 后端代码已经在 `backend/src/main/java/com/heartsphere/mentis/`
   - 迁移到 `mentis/backend/`
   - 更新 API 路径前缀为 `/api/mentis/`（可能已经存在）

### 阶段 6: 清理和优化（1-2 周）

1. **清理旧代码**：
   - 删除旧的目录结构
   - 清理无用的配置文件
   - 更新文档和脚本

2. **优化和测试**：
   - 优化构建配置
   - 完善测试覆盖
   - 性能测试和优化

3. **文档更新**：
   - 更新开发文档
   - 更新部署文档
   - 更新 API 文档

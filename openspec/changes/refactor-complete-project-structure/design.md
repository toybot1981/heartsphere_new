# Design: 全面重构 - 完整的项目结构拆分

## Context

基于之前的子项目拆分工作，当前 HeartSphere 项目已经初步拆分为 edu、mentis、company 三个子项目，并创建了 shared 模块。现在需要进一步优化和完善，实现完整的项目结构拆分，包括：

1. 所有客户端产品完全独立
2. 统一管理后台（admin）能够管理所有产品
3. 共享代码独立管理

## Goals / Non-Goals

### Goals

1. **完全独立的客户端产品**：
   - client、edu、mentis、company 四个产品完全独立
   - 每个产品都有独立的前后端
   - 每个产品可以独立开发、部署和扩展

2. **统一的管理后台**：
   - 一个 admin 入口管理所有产品
   - 统一的管理界面和功能
   - 统一的权限和用户管理

3. **独立的共享模块**：
   - shared 模块真正独立，便于版本管理
   - 清晰的职责边界和使用规范
   - 易于维护和扩展

4. **清晰的依赖关系**：
   - 各子项目之间的依赖关系明确
   - 避免循环依赖
   - 依赖版本统一管理

### Non-Goals

1. **不完全拆分为微服务**：
   - 暂时不考虑将每个子项目拆分为独立的微服务
   - 每个子项目的后端仍然是一个 Spring Boot 应用
   - 未来可以考虑微服务化，但不在本次重构范围内

2. **不改变现有的技术栈**：
   - 保持现有的技术栈（Spring Boot、React、TypeScript 等）
   - 不引入新的框架或技术
   - 只优化项目结构，不改变技术实现

3. **不统一 UI 风格**：
   - 不强制所有产品使用相同的 UI 风格
   - 每个产品可以有自己的 UI 设计
   - shared/frontend 中的公共组件是可选的

## Decisions

### Decision: 项目结构

**决定**：采用扁平化的项目结构，每个子项目都在根目录下。

**理由**：
- 便于理解和导航
- 避免过深的目录层级
- 便于 CI/CD 配置和部署

**替代方案**：
- 按产品类型分组（如 `products/client/`、`products/edu/`），但会增加目录层级
- 按前后端分组（如 `frontends/`、`backends/`），但不利于产品维度的管理

### Decision: 管理后台统一管理

**决定**：使用一个统一的管理后台（admin）来管理所有客户端产品。

**理由**：
- 便于统一管理和监控
- 减少管理成本
- 提供一致的管理体验

**实现方式**：
- admin 后端提供统一的 API 来管理各产品
- admin 前端提供统一的管理界面
- 各产品通过 admin 进行配置和管理，而不是直接管理

**替代方案**：
- 每个产品独立的管理后台，但会增加管理复杂度
- 分散的管理入口，不利于统一管理

### Decision: 共享模块管理

**决定**：使用 Maven 多模块（backend）和 npm/yarn workspace（frontend）来管理共享代码。

**理由**：
- 便于版本管理和依赖控制
- 支持本地开发和构建
- 与现有工具链兼容

**实现方式**：
- shared/backend 作为 Maven 模块，被各子项目的 backend 依赖
- shared/frontend 作为 npm/yarn workspace，被各子项目的 frontend 引用
- 版本号统一管理，避免版本冲突

**替代方案**：
- Git Submodule：但会增加 Git 操作的复杂度
- 独立的 npm 包/Maven 仓库：但需要额外的发布和维护工作

### Decision: 依赖关系

**决定**：各子项目依赖 shared 模块，但不直接依赖其他子项目。admin 通过 API 调用各产品。

**依赖关系**：
```
client/backend  ──┐
edu/backend     ──┤
mentis/backend  ──┼──> shared/backend
company/backend ──┤
admin/backend   ──┘

client/frontend  ──┐
edu/frontend     ──┤
mentis/frontend  ──┼──> shared/frontend
company/frontend ──┤
admin/frontend   ──┘

admin/backend ──API──> client/backend
                    └──> edu/backend
                    └──> mentis/backend
                    └──> company/backend
```

**理由**：
- 避免循环依赖
- 保持各子项目的独立性
- admin 通过 API 调用各产品，实现解耦

**替代方案**：
- 各子项目直接依赖其他子项目：但会增加耦合度
- 使用消息队列进行通信：但会增加系统复杂度

## Risks / Trade-offs

### Risk 1: 迁移复杂度高

**风险**：将现有代码迁移到新的项目结构需要大量工作，可能会引入 bug。

**缓解措施**：
1. 分阶段迁移，逐步完成
2. 每个阶段都进行充分的测试
3. 保持向后兼容，逐步切换

### Risk 2: 共享代码版本冲突

**风险**：各子项目对 shared 模块的版本需求不同，可能导致版本冲突。

**缓解措施**：
1. 统一的版本管理策略
2. 向后兼容的 API 设计
3. 清晰的版本发布和升级流程

### Risk 3: 管理后台性能问题

**风险**：统一管理后台需要聚合多个产品的数据，可能导致性能问题。

**缓解措施**：
1. 异步加载和分页
2. 缓存机制
3. 按需加载数据
4. 考虑使用 GraphQL 聚合查询

### Risk 4: 构建和部署复杂度增加

**风险**：多个子项目需要独立的构建和部署流程，可能增加 CI/CD 的复杂度。

**缓解措施**：
1. 统一的构建脚本和模板
2. 自动化的 CI/CD 配置
3. 清晰的部署文档和流程

## Migration Plan

### Phase 1: 完善现有子项目（1-2 周）

1. 完善 edu、mentis、company 的项目结构
2. 修复依赖关系和构建问题
3. 确保各子项目可以独立运行

### Phase 2: 整合管理后台（2-3 周）

1. 整合现有的管理端代码（`frontend/admin/`、`admin-edu/` 等）
2. 创建统一的 admin 项目结构
3. 实现统一的管理 API 和界面
4. 迁移各产品的管理功能到 admin

### Phase 3: 提取共享代码（1-2 周）

1. 进一步识别和提取共享代码
2. 完善 shared 模块的结构和功能
3. 更新各子项目使用 shared 模块
4. 编写共享代码的使用文档

### Phase 4: 迁移主客户端（2-3 周）

1. 迁移主客户端代码到 client/ 目录
2. 拆分 PC、Mobile、小程序三个版本
3. 更新依赖关系和配置
4. 测试各版本的运行

### Phase 5: 测试和优化（1-2 周）

1. 全面测试各子项目的功能
2. 优化构建和部署流程
3. 完善文档和规范
4. 性能测试和优化

## Open Questions

1. **主客户端（client）的定位**：
   - client 是否包含所有核心功能（AI对话、场景管理等）？
   - 还是 client 只是一个轻量级的入口，实际功能在各产品中？

2. **管理后台的权限模型**：
   - 是否需要细粒度的权限控制（如只能管理特定产品）？
   - 还是所有管理员都有全部权限？

3. **共享 UI 组件的范围**：
   - 是否需要强制所有产品使用相同的 UI 组件库？
   - 还是只提供基础组件，各产品可以自定义？

4. **数据共享策略**：
   - 各产品之间的数据是否需要共享？
   - 如果需要，如何实现数据共享（数据库共享、API 调用、消息队列等）？

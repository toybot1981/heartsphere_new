# Change: Refactor Guest Mode to Create Individual Temporary Users

## Why

当前游客模式实现使用固定的 `__guest__` 用户，所有游客共享同一个用户账号和会员额度。这种设计存在以下问题：

1. **额度共享问题**: 所有游客共享同一个会员额度，导致：
   - 无法为每个游客单独分配和跟踪Token配额
   - 一个游客消耗完额度会影响其他游客
   - 无法准确统计每个游客的使用情况

2. **数据隔离问题**: 所有游客的数据混在一起，无法：
   - 区分不同游客的对话记录
   - 为每个游客提供独立的使用体验
   - 在游客升级为正式用户时准确迁移数据

3. **配额管理问题**: 无法为每个游客单独：
   - 分配独立的会员额度
   - 跟踪每个游客的Token消耗
   - 实现个性化的配额限制

因此，需要将游客模式改为为每个游客创建独立的临时用户账号，每个游客拥有独立的会员记录和配额。

## What Changes

### Core Changes

- **MODIFIED**: 游客登录逻辑 - 为每个游客创建独立的临时用户账号（而不是使用固定的 `__guest__` 用户）
- **MODIFIED**: 会员分配逻辑 - 为每个游客用户单独创建体验会员记录
- **MODIFIED**: 配额管理逻辑 - 每个游客拥有独立的Token配额和使用记录
- **ADDED**: 临时用户标识 - 通过用户名格式或用户属性标识临时用户
- **ADDED**: 临时用户清理机制 - 定期清理长期未使用的临时用户账号

### Database Changes

- **MODIFIED**: 游客登录时创建新的 `users` 表记录（而不是查找固定的 `__guest__` 用户）
- **MODIFIED**: 为每个游客用户创建独立的 `memberships` 表记录
- **ADDED**: 用户表可能需要添加 `is_temporary` 字段或通过用户名格式标识临时用户

### API Changes

- **MODIFIED**: `POST /api/auth/guest-login` - 每次调用创建新的临时用户，而不是复用固定用户
- **MODIFIED**: 会员服务 - 为每个临时用户创建独立的会员记录
- **MODIFIED**: 配额服务 - 为每个临时用户分配独立的配额

### Behavior Changes

- **MODIFIED**: 游客不再共享用户账号和会员额度
- **MODIFIED**: 每个游客拥有独立的对话记录和使用数据
- **ADDED**: 临时用户清理策略（如30天未使用自动清理）

## Impact

- **Affected specs**: 
  - 用户认证（authentication）
  - 会员管理（membership-management）
  - 配额管理（quota-management）

- **Affected code**:
  - `AuthController.guestLogin()` - 改为创建新用户而不是查找固定用户
  - `MembershipService.getOrCreateTrialMembership()` - 为每个用户创建独立会员
  - `TokenQuotaService` - 为每个用户分配独立配额
  - 数据库迁移脚本 - 移除固定的 `__guest__` 用户（可选）

- **Database**:
  - `users` 表 - 每个游客创建新记录
  - `memberships` 表 - 每个游客创建新记录
  - 可能需要添加临时用户标识字段

## Design Principles

1. **独立隔离**: 每个游客拥有独立的用户账号、会员记录和配额
2. **自动创建**: 游客登录时自动创建临时用户，无需手动管理
3. **配额独立**: 每个游客拥有独立的1万文本Token配额
4. **数据隔离**: 每个游客的对话记录和使用数据完全隔离
5. **平滑升级**: 临时用户升级为正式用户时，数据迁移更准确
6. **资源清理**: 定期清理长期未使用的临时用户，避免数据库膨胀

## User Experience Flow

1. **游客登录**: 用户选择"游客模式" → 调用 `POST /api/auth/guest-login` → 系统创建新的临时用户（用户名格式：`guest_<timestamp>_<random>`） → 为该用户创建独立的体验会员 → 分配独立的1万文本Token配额 → 登录成功

2. **配额使用**: 每个游客独立使用自己的1万文本Token配额，互不影响

3. **数据隔离**: 每个游客的对话记录、使用数据完全独立

4. **升级流程**: 游客注册为正式用户 → 更新临时用户信息为正式用户 → 会员类型升级 → 数据保留

## Risks & Mitigation

- **风险1**: 临时用户账号大量增长，导致数据库膨胀
  - **缓解**: 实现临时用户清理机制，定期清理长期未使用的账号（如30天未使用）
  - **缓解**: 限制单个IP的游客账号创建频率

- **风险2**: 临时用户创建失败导致登录失败
  - **缓解**: 实现重试机制和错误处理
  - **缓解**: 记录详细的错误日志

- **风险3**: 临时用户升级为正式用户时数据迁移复杂
  - **缓解**: 由于每个游客数据独立，迁移逻辑更简单清晰
  - **缓解**: 提供数据迁移验证机制

## Success Criteria

- [ ] 每次游客登录创建新的独立临时用户账号
- [ ] 每个临时用户拥有独立的体验会员记录
- [ ] 每个临时用户拥有独立的1万文本Token配额
- [ ] 临时用户的配额使用互不影响
- [ ] 临时用户的对话记录完全隔离
- [ ] 临时用户升级为正式用户时数据正确迁移
- [ ] 实现临时用户清理机制（可选，但推荐）

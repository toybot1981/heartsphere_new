# Design: 主项目重构为基础设施服务

## Context

当前 HeartSphere 项目包含多个子项目：
- **主项目**（frontend + backend）：提供核心的数字生命体交互功能
- **mentis**：心理健康相关项目
- **edu**：教育版项目
- **admin**：统一管理后台

主项目未来将转型为基础设施服务提供者，为其他项目提供：
- 场景角色剧本服务
- AIAgent 服务
- 其他底层基础服务

## Goals / Non-Goals

### Goals
- 明确主项目的定位：基础设施服务提供者
- 将主项目代码迁移到 `main/` 目录，与其他项目平级
- 清理主项目中的 edu 相关代码，避免功能重复
- 确保项目间通过 API 通信，而非代码依赖
- 保持向后兼容性，最小化对现有功能的影响

### Non-Goals
- 不改变主项目的核心功能（AI对话、场景管理、角色扮演等）
- 不重构 mentis、edu、admin 的内部架构（仅清理耦合）
- 不改变数据库结构（除非必要）
- 不改变 API 接口（除非需要明确基础设施服务接口）

## Decisions

### Decision 1: 目录结构重组
**决策**：将 `frontend` 和 `backend` 迁移到 `main/` 目录下

**理由**：
- 明确主项目作为基础设施服务的定位
- 与其他项目（mentis、edu、admin）保持平级结构
- 便于未来扩展更多基础设施服务

**目录结构**：
```
heartsphere_new/
├── main/
│   ├── frontend/     # 主项目前端
│   └── backend/      # 主项目后端
├── mentis/           # 心理健康项目
├── edu/              # 教育版项目
├── admin/            # 管理后台
└── shared/           # 公共模块
```

**替代方案考虑**：
- 保持当前结构：不清晰，主项目定位不明确
- 重命名为 `foundation` 或 `core`：`main` 更直观，表示主项目

### Decision 2: Edu 代码清理策略
**决策**：从主项目中移除所有 edu 相关的代码和配置

**理由**：
- `edu` 已经作为独立项目存在，功能完整
- 避免代码重复和维护负担
- 明确职责边界

**清理范围**：
- 后端：edu 相关的 Controller、Service、Entity、Repository
- 前端：edu 相关的页面、组件、路由
- 配置：edu 相关的配置项、路由配置
- 数据库迁移：edu 相关的迁移脚本（如果存在）

**保留内容**：
- 基础设施服务（场景、角色、AI 等）的通用功能
- 如果 edu 项目依赖主项目的基础设施服务，保留这些服务接口

**替代方案考虑**：
- 保留 edu 代码但标记为废弃：增加维护负担，不符合目标
- 仅清理明显重复的代码：不够彻底，边界不清

### Decision 3: 项目间通信方式
**决策**：项目间通过 HTTP API 调用主项目的基础设施服务

**理由**：
- 符合微服务架构原则
- 保持项目独立性
- 便于未来扩展和部署

**通信方式**：
- mentis、edu、admin 通过 HTTP 调用主项目的 RESTful API
- 主项目提供明确的基础设施服务接口文档
- 使用标准的 HTTP 认证（JWT）

**禁止的通信方式**：
- ❌ 直接依赖主项目的 Java 类或 TypeScript 类型（业务逻辑）
- ❌ 共享数据库表（除非是基础设施相关的表）
- ✅ 允许：调用主项目的 API 接口
- ✅ 允许：使用 shared 模块的公共类型定义

**替代方案考虑**：
- 使用消息队列：过度设计，当前不需要异步通信
- 共享代码库：违反项目独立性原则

### Decision 4: 基础设施服务接口设计
**决策**：主项目提供明确的基础设施服务 API，包括场景角色剧本、AIAgent 等服务

**接口范围**（待细化）：
- 场景管理服务：创建、查询、更新场景
- 角色管理服务：创建、查询、更新角色
- 剧本服务：创建、查询、执行剧本
- AIAgent 服务：AI 对话、技能调用等

**接口规范**：
- 使用 RESTful API 设计
- 提供 OpenAPI/Swagger 文档
- 版本控制：`/api/v1/...`

**替代方案考虑**：
- GraphQL：当前 RESTful 已足够，未来可考虑
- gRPC：过度设计，HTTP 更简单

## Risks / Trade-offs

### Risk 1: 路径引用更新遗漏
**风险**：迁移后，某些脚本或配置文件中的路径引用未更新，导致构建或部署失败

**缓解措施**：
- 使用全局搜索（`rg`）查找所有路径引用
- 创建路径更新检查清单
- 在测试环境充分验证

### Risk 2: Edu 代码清理过度
**风险**：清理了 edu 项目实际依赖的基础设施服务代码

**缓解措施**：
- 先分析 edu 项目的依赖关系
- 明确区分"edu 业务代码"和"基础设施服务"
- 保留基础设施服务的通用功能

### Risk 3: 项目间 API 调用性能
**风险**：通过 HTTP 调用可能比直接代码调用慢

**缓解措施**：
- 当前项目规模下，HTTP 调用性能可接受
- 未来可考虑使用连接池、缓存等优化
- 监控 API 调用性能，必要时优化

### Risk 4: 向后兼容性
**风险**：迁移后，现有功能可能受影响

**缓解措施**：
- 保持 API 接口不变（除非明确需要变更）
- 充分测试现有功能
- 提供迁移指南和回滚方案

## Migration Plan

### Phase 1: 准备阶段
1. 分析当前项目结构和依赖关系
2. 识别所有需要清理的 edu 相关代码
3. 识别所有路径引用需要更新的位置
4. 创建详细的迁移检查清单

### Phase 2: 代码清理
1. 从主项目 backend 中移除 edu 相关代码
2. 从主项目 frontend 中移除 edu 相关代码
3. 从 mentis、admin 中清理 edu 相关代码（如果存在）
4. 验证清理后项目仍可正常编译

### Phase 3: 目录迁移
1. 创建 `main/` 目录
2. 迁移 `frontend/` → `main/frontend/`
3. 迁移 `backend/` → `main/backend/`
4. 更新所有路径引用（构建脚本、配置文件、文档等）

### Phase 4: 验证和测试
1. 验证所有项目可正常构建
2. 验证所有项目可正常启动
3. 验证项目间 API 调用正常
4. 更新文档

### Rollback Plan
如果迁移失败：
1. 恢复 `main/frontend/` → `frontend/`
2. 恢复 `main/backend/` → `backend/`
3. 恢复所有路径引用
4. 恢复被清理的代码（如果有备份）

## Open Questions

1. **基础设施服务 API 的具体范围**：需要明确哪些服务属于"基础设施服务"，哪些属于"业务服务"
2. **数据库表共享策略**：基础设施相关的表（如场景、角色）是否需要共享，还是每个项目独立
3. **认证和授权**：项目间 API 调用的认证方式（是否使用统一的 JWT，还是各自独立）
4. **版本管理**：基础设施服务 API 的版本管理策略

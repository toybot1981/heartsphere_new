# Design: 完善 web-automation-testing 技能的日志检查和自动修复功能

## Context

web-automation-testing 技能当前能够自动修复测试用例级别的问题（如选择器错误、等待条件不足），但无法处理服务级别的问题。当测试失败是由于前后端服务异常导致时，需要：

1. 检查服务日志，识别服务错误
2. 根据错误类型，尝试自动修复
3. 使用项目标准启动脚本重启服务

## Goals / Non-Goals

### Goals
- 在测试失败时自动检查相关服务的日志文件
- 识别常见的服务错误模式（端口占用、数据库连接失败、配置错误等）
- 自动修复可修复的服务问题（如重启服务）
- 使用项目标准启动脚本（`scripts/start/`）进行服务重启
- 在服务修复后自动重试测试
- 持续测试循环：测试失败后自动修复并重试，直到所有测试通过或被人为打断

### Non-Goals
- 不修复代码级别的错误（如语法错误、逻辑错误）
- 不修改服务配置文件的复杂问题（如数据库连接字符串错误）
- 不处理需要人工干预的问题（如权限问题、资源不足）

## Decisions

### Decision 1: 日志文件位置确定策略
**决策**：通过以下方式确定日志文件位置（按优先级）：
1. **从启动脚本解析**：解析启动脚本中的输出重定向（如 `> "$PROJECT_ROOT/main/backend-backend.log"`），提取日志文件路径
2. **服务配置映射**：维护服务名称到日志路径的映射配置，支持不同项目的日志路径差异
3. **默认路径尝试**：如果无法从启动脚本解析，尝试常见路径：
   - 项目根目录下的日志文件（如 `{service}-backend.log`, `{service}-frontend.log`）
   - `logs/` 目录下的日志文件（如 `logs/application.log`）

**原因**：
- 不同项目有不同的日志路径模式（如 main 项目使用 `main/backend-backend.log`，admin 项目使用 `admin-backend.log`）
- 启动脚本中明确指定了日志路径，应该从脚本中解析以确保准确性
- 需要支持项目间的差异，同时提供灵活的配置方式

**实现**：
- 服务管理器解析启动脚本，提取日志路径（通过正则表达式匹配 `> "..."` 或 `> '...'` 模式）
- 维护服务配置映射表，包含服务名称、启动脚本路径、日志路径模式
- 日志分析器根据服务名称查找对应的日志文件路径
- 支持通过配置文件覆盖默认映射

### Decision 2: 服务到启动脚本和日志路径的映射
**决策**：维护服务配置映射，包含服务名称、启动脚本路径和日志路径模式：
- `main-backend` → 脚本：`scripts/start/start-main-backend.sh`，日志：`main/backend-backend.log`（从脚本解析）
- `main-frontend` → 脚本：`scripts/start/start-main-frontend.sh`，日志：`main/frontend-frontend.log`（从脚本解析）
- `admin-backend` → 脚本：`scripts/start/start-admin-backend.sh`，日志：`admin-backend.log`（从脚本解析）
- `admin-frontend` → 脚本：`scripts/start/start-admin-frontend.sh`，日志：`admin-frontend.log`（从脚本解析）
- 等等

**原因**：
- 不同项目有不同的日志路径模式，需要明确映射关系
- 启动脚本中包含了准确的日志路径信息，应该从脚本中解析
- 需要支持项目间的差异，同时保持配置的灵活性

**实现**：
- 服务管理器维护服务配置映射表（JSON 或 Python 字典）
- 首次使用时，解析启动脚本提取日志路径并缓存
- 支持通过配置文件扩展或覆盖映射关系
- 在 SKILL.md 中说明各项目的日志路径和启动脚本差异

### Decision 3: 错误模式识别策略
**决策**：使用基于关键词和正则表达式的模式匹配识别常见错误：
- 端口占用：`Address already in use`, `Port.*already in use`
- 数据库连接失败：`Connection refused`, `Access denied`, `Unknown database`
- 配置错误：`Configuration error`, `Missing property`
- 编译错误：`Compilation failure`, `Cannot resolve`

**原因**：这些是常见的服务启动错误，可以通过模式匹配识别。

**实现**：
- 日志分析器维护错误模式字典
- 支持通过配置文件扩展错误模式

### Decision 4: 服务重启策略
**决策**：在修复服务问题后，使用标准启动脚本重启服务，并等待服务就绪：
1. 检查服务是否正在运行（通过 PID 文件或端口）
2. 如果运行，先停止服务
3. 使用标准启动脚本启动服务
4. 等待服务就绪（通过健康检查端点或端口监听）

**原因**：确保服务完全重启并可用后再重试测试。

**实现**：
- 服务管理器实现服务停止和启动逻辑
- 添加健康检查等待机制（最多等待 60 秒）

### Decision 5: 持续测试循环策略
**决策**：测试运行器实现持续测试循环，不设置最大迭代次数限制（或设置为非常大的值），循环执行以下流程直到成功或中断：
1. 执行测试
2. 如果测试失败：
   - 检查服务日志，识别服务问题
   - 修复服务问题（如重启服务）
   - 修复测试用例问题（如更新选择器）
   - 自动重试测试
3. 如果测试通过，结束循环
4. 支持人为中断（如 Ctrl+C），优雅停止并保存当前状态

**原因**：
- 自动化测试应该能够持续运行直到成功，减少人工干预
- 某些问题可能需要多次修复迭代才能解决
- 支持人为中断确保用户可以随时停止测试

**实现**：
- 测试运行器移除或大幅提高最大迭代次数限制（如 1000 次）
- 实现信号处理（SIGINT, SIGTERM），支持优雅中断
- 在每次迭代中检查中断信号，如果收到中断请求，保存当前状态并退出
- 记录每次迭代的修复历史，便于分析
- 在控制台输出中显示当前迭代次数和修复进度

## Risks / Trade-offs

### Risk 1: 日志文件可能不存在或不可读
**风险**：某些服务可能没有日志文件，或日志文件权限不足。

**缓解**：
- 检查日志文件是否存在和可读
- 如果不可用，跳过日志检查，仅进行测试用例修复

### Risk 2: 自动修复可能失败或导致副作用
**风险**：自动修复可能无法解决问题，或导致其他问题。

**缓解**：
- 限制自动修复的范围（仅处理明确可修复的问题）
- 在修复前备份当前状态
- 记录所有修复操作，便于回滚

### Risk 3: 服务重启可能影响其他测试
**风险**：重启服务可能影响正在运行的其他测试或服务。

**缓解**：
- 仅在测试失败且确认是服务问题时才重启
- 支持配置禁用自动重启功能

### Risk 4: 持续测试可能陷入无限循环
**风险**：如果问题无法自动修复，测试可能无限循环。

**缓解**：
- 检测修复无效的情况（如连续多次修复后测试仍然失败且修复内容相同）
- 在检测到无效修复时，停止循环并报告需要人工干预
- 支持人为中断（Ctrl+C），用户可以随时停止
- 记录所有修复历史，便于分析问题

## Migration Plan

### Phase 1: 实现核心功能
1. 实现日志分析器（`log_analyzer.py`）
2. 实现服务管理器（`service_manager.py`）
3. 集成到测试修复流程

### Phase 2: 测试和优化
1. 测试各种错误场景
2. 优化错误模式识别
3. 完善文档和示例

### Phase 3: 扩展和增强
1. 支持更多错误模式
2. 支持更多服务类型
3. 添加配置选项

## Open Questions

1. **日志文件格式**：不同服务的日志格式可能不同，是否需要支持多种格式？
   - 当前决策：先支持常见的文本日志格式，后续根据需要扩展

2. **服务依赖**：某些服务可能依赖其他服务，重启时是否需要处理依赖关系？
   - 当前决策：先处理单个服务的重启，后续根据需要添加依赖处理

3. **并发测试**：多个测试同时运行时，服务重启可能冲突，是否需要加锁？
   - 当前决策：先实现单进程场景，后续根据需要添加并发控制

4. **持续测试的最大迭代次数**：是否应该设置最大迭代次数限制？
   - 当前决策：不设置硬性限制，但检测无效修复（连续多次相同修复）时停止，并支持人为中断

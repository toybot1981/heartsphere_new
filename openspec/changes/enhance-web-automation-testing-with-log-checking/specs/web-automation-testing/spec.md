## ADDED Requirements

### Requirement: 日志文件检查和错误识别
系统 SHALL 在测试失败时自动检查相关前后端服务的日志文件，识别服务级别的错误。

#### Scenario: 测试失败时检查后端日志
- **WHEN** 测试执行失败
- **AND** 测试计划中指定了后端服务（如 `main-backend`）
- **THEN** 系统根据服务配置映射表确定日志文件路径：
  - 从启动脚本（如 `scripts/start/start-main-backend.sh`）中解析日志路径
  - 或使用配置映射表中的日志路径（如 `main/backend-backend.log` 或 `admin-backend.log`）
- **AND** 自动读取后端服务的日志文件
- **AND** 分析日志内容，识别错误模式（如端口占用、数据库连接失败等）

#### Scenario: 测试失败时检查前端日志
- **WHEN** 测试执行失败
- **AND** 测试计划中指定了前端服务（如 `main-frontend`）
- **THEN** 系统根据服务配置映射表确定日志文件路径：
  - 从启动脚本（如 `scripts/start/start-main-frontend.sh`）中解析日志路径
  - 或使用配置映射表中的日志路径（如 `main/frontend-frontend.log` 或 `admin-frontend.log`）
- **AND** 自动读取前端服务的日志文件
- **AND** 分析日志内容，识别错误模式（如编译错误、端口占用等）

#### Scenario: 从启动脚本解析日志路径
- **WHEN** 系统需要确定服务的日志文件路径
- **AND** 启动脚本存在（如 `scripts/start/start-main-backend.sh`）
- **THEN** 系统解析启动脚本中的输出重定向（如 `> "$PROJECT_ROOT/main/backend-backend.log"`）
- **AND** 提取日志文件路径（支持 `$PROJECT_ROOT` 变量替换）
- **AND** 将解析结果缓存到服务配置映射表中

#### Scenario: 支持不同项目的日志路径差异
- **WHEN** 系统需要确定不同项目的日志路径
- **THEN** 系统支持不同的日志路径模式：
  - main 项目：`main/backend-backend.log`, `main/frontend-frontend.log`
  - admin 项目：`admin-backend.log`, `admin-frontend.log`
  - edu 项目：`edu-backend.log`, `edu-frontend.log`
  - 其他项目：根据启动脚本解析或配置映射
- **AND** 在 SKILL.md 中说明各项目的日志路径和启动脚本差异

#### Scenario: 日志文件不存在时跳过检查
- **WHEN** 测试执行失败
- **AND** 指定的日志文件不存在或不可读
- **THEN** 系统跳过日志检查，继续执行测试用例修复流程
- **AND** 在报告中记录日志文件不可用的警告

### Requirement: 服务问题自动诊断
系统 SHALL 根据日志分析结果，自动诊断服务问题并确定是否需要修复。

#### Scenario: 识别端口占用错误
- **WHEN** 日志分析发现端口占用错误（如 "Address already in use"）
- **THEN** 系统识别为端口占用问题
- **AND** 标记为可自动修复的问题类型

#### Scenario: 识别数据库连接错误
- **WHEN** 日志分析发现数据库连接错误（如 "Connection refused"）
- **THEN** 系统识别为数据库连接问题
- **AND** 标记为需要人工干预的问题类型（不自动修复）

#### Scenario: 识别配置错误
- **WHEN** 日志分析发现配置错误（如 "Missing property"）
- **THEN** 系统识别为配置问题
- **AND** 标记为需要人工干预的问题类型（不自动修复）

### Requirement: 服务自动修复和重启
系统 SHALL 对于可自动修复的服务问题，使用项目标准启动脚本进行服务重启。

#### Scenario: 重启后端服务
- **WHEN** 诊断发现需要重启后端服务（如端口占用）
- **AND** 服务名称为 `main-backend`
- **THEN** 系统检查服务是否正在运行（通过 PID 文件或端口）
- **AND** 如果运行，先停止服务
- **AND** 使用 `scripts/start/start-main-backend.sh` 启动服务
- **AND** 等待服务就绪（通过健康检查或端口监听，最多等待 60 秒）

#### Scenario: 重启前端服务
- **WHEN** 诊断发现需要重启前端服务（如编译错误）
- **AND** 服务名称为 `main-frontend`
- **THEN** 系统检查服务是否正在运行
- **AND** 如果运行，先停止服务
- **AND** 使用 `scripts/start/start-main-frontend.sh` 启动服务
- **AND** 等待服务就绪（通过端口监听，最多等待 60 秒）

#### Scenario: 服务重启失败处理
- **WHEN** 服务重启失败（如启动脚本执行失败）
- **THEN** 系统记录错误信息
- **AND** 在修复报告中标记服务修复失败
- **AND** 继续执行测试用例修复流程（不阻止后续修复尝试）

### Requirement: 修复流程集成
系统 SHALL 将日志检查和修复流程集成到现有的测试修复流程中。

#### Scenario: 测试失败时的完整修复流程
- **WHEN** 测试执行失败
- **THEN** 系统首先执行日志检查
- **AND** 如果发现服务问题，尝试自动修复
- **AND** 然后执行测试用例修复（更新选择器、添加等待条件等）
- **AND** 在修复报告中记录所有修复操作

#### Scenario: 服务修复后的测试重试
- **WHEN** 服务修复成功
- **AND** 测试用例修复完成
- **THEN** 系统等待服务就绪
- **AND** 自动重新执行测试（不等待人工干预）
- **AND** 在报告中记录服务修复和重试历史

#### Scenario: 修复报告包含服务修复信息
- **WHEN** 执行了服务修复操作
- **THEN** 修复报告中包含：
  - 检查的日志文件路径（从启动脚本解析或配置映射获取）
  - 使用的启动脚本路径
  - 识别的错误类型
  - 执行的修复操作（如服务重启）
  - 修复结果（成功/失败）

### Requirement: 持续测试循环
系统 SHALL 实现持续测试循环，自动修复并重试测试，直到所有测试通过或被人为打断。

#### Scenario: 持续测试直到成功
- **WHEN** 测试执行失败
- **THEN** 系统自动执行修复流程（日志检查、服务修复、测试用例修复）
- **AND** 修复完成后自动重试测试
- **AND** 如果重试后仍然失败，重复修复和重试流程
- **AND** 循环执行直到所有测试通过
- **AND** 不设置最大迭代次数限制（或设置为非常大的值，如 1000 次）

#### Scenario: 人为中断测试
- **WHEN** 用户发送中断信号（如 Ctrl+C）
- **THEN** 系统优雅停止当前测试迭代
- **AND** 保存当前测试状态和修复历史
- **AND** 生成当前状态的报告
- **AND** 退出测试流程

#### Scenario: 检测无效修复并停止
- **WHEN** 连续多次（如 5 次）修复后测试仍然失败
- **AND** 修复内容相同（没有新的修复尝试）
- **THEN** 系统检测到无效修复
- **AND** 停止持续测试循环
- **AND** 在报告中标记需要人工干预
- **AND** 输出所有修复历史供分析

#### Scenario: 显示测试进度
- **WHEN** 持续测试循环运行中
- **THEN** 系统在控制台输出中显示：
  - 当前迭代次数
  - 当前测试状态（通过/失败）
  - 执行的修复操作
  - 修复进度提示

## MODIFIED Requirements

### Requirement: 测试失败分析和修复
系统 SHALL 在测试失败时分析失败原因，并尝试自动修复测试用例和服务问题，然后自动重试测试。

#### Scenario: 测试失败时的完整分析
- **WHEN** 测试执行失败
- **THEN** 系统分析失败原因：
  - 检查服务日志，识别服务级别错误
  - 分析测试步骤，识别测试用例级别错误
- **AND** 根据分析结果，确定修复策略：
  - 如果是服务问题，尝试自动修复服务
  - 如果是测试用例问题，尝试修复测试用例
- **AND** 修复完成后自动重试测试（不等待人工干预）

#### Scenario: 服务修复后的测试重试
- **WHEN** 服务修复成功
- **AND** 测试用例修复完成
- **THEN** 系统等待服务就绪（最多 60 秒）
- **AND** 自动重新执行测试（不等待人工干预）
- **AND** 在报告中记录服务修复和重试历史
- **AND** 如果测试仍然失败，继续执行修复和重试流程

# Design: Manus AI 风格虚拟电脑系统

## Context

参考 Manus AI 的成功实现（详见 `docs/MANUS_ANALYSIS_REPORT.md`），我们需要在 HeartSphere 项目中实现一个类似的虚拟电脑系统。当前 Mentis 系统已有基础的虚拟机管理和任务执行能力，但需要增强为完整的虚拟电脑环境。

## Goals / Non-Goals

### Goals
- 提供完整的虚拟电脑环境（桌面、浏览器、终端）
- 实现 Planner + Executor + Monitor 三智能体协作架构
- 实现 27 种工具覆盖常见操作场景
- 支持长期任务（最长14天）和会话持久化
- 提供流式交互体验，实时展示 AI 思考过程

### Non-Goals
- 不强制使用 E2B 平台（优先自建 Docker 方案）
- 不实现完整的操作系统（使用现有 Linux 发行版）
- 不实现所有 Manus 的功能（聚焦核心能力）
- 不改变现有 Mentis 系统的核心架构（在现有基础上增强）

## Decisions

### Decision 1: 虚拟化技术选型

**选择**: E2B 平台作为主要方案（与 Manus AI 一致），保留 Docker 作为备选方案

**理由**:
- E2B 是 Manus AI 使用的成熟方案，已验证可行
- 启动速度极快（~150ms），远超 Docker（10-20秒）
- 完整操作系统级别隔离，安全性高
- 开箱即用，无需自建基础设施
- 支持完整桌面环境（XFCE4 + VNC + Chromium）
- 支持持久化会话（最长14天）和检查点
- 按使用付费，初期成本可控

**备选方案**: Docker
- 优势：技术成熟，社区支持好，成本低（自建）
- 劣势：启动速度慢（10-20秒），隔离级别较低（容器级）
- 使用场景：E2B 不可用时的降级方案，或未来成本优化考虑
- 保留实现：保留 Docker 实现代码，但不作为主要方案使用

### Decision 2: 桌面环境选型

**选择**: XFCE4 轻量级桌面环境

**理由**:
- 轻量级，资源占用低
- 支持 VNC 远程桌面
- 易于自动化（支持 GUI 操作）
- 与 Manus 方案一致

### Decision 3: 浏览器自动化选型

**选择**: Playwright（优先）或 Selenium WebDriver

**理由**:
- Playwright 性能更好，支持多浏览器
- 更好的无头浏览器支持
- 更现代的 API 设计
- 如果 Playwright 集成困难，可降级到 Selenium

### Decision 4: 多智能体框架选型

**选择**: 基于现有 AgentScope 集成，或实现类似 LangGraph 的状态机

**理由**:
- 项目已集成 AgentScope，可复用现有能力
- 如果 AgentScope 不支持复杂状态机，可自建基于状态机的编排
- 保持与现有 Mentis 系统的一致性

### Decision 5: 实时通信选型

**选择**: WebSocket（双向） + SSE（单向推送）

**理由**:
- WebSocket 用于双向通信（如用户输入、控制命令）
- SSE 用于服务器向客户端推送（如任务进度、截图）
- 前端已有 WebSocket 支持，易于集成

### Decision 6: 会话持久化策略

**选择**: 数据库存储 + 文件系统存储

**理由**:
- 会话元数据存储在数据库（状态、检查点信息）
- 沙箱状态通过 Docker 镜像快照或文件系统快照保存
- 平衡性能和成本

### 数据流

```
用户请求
  ↓
Planner Agent (任务分解)
  ↓
Executor Agent (执行工具)
  ├─→ Tool Registry (工具调用)
  ├─→ Sandbox Manager (沙箱操作)
  └─→ Streaming Service (进度推送)
  ↓
Monitor Agent (状态监控)
  ├─→ 异常检测
  ├─→ 自动恢复
  └─→ 状态更新
  ↓
返回结果 / 继续执行
```

## Risks / Trade-offs

### Risk 1: E2B 平台依赖和成本
**缓解措施**:
- E2B 提供免费套餐（每月1,000次调用），适合初期验证
- 监控 E2B 使用量，优化调用频率
- 保留 Docker 实现作为降级方案
- 未来如果成本过高，可评估自建 Firecracker 方案

### Risk 2: 多智能体协作复杂度高
**缓解措施**:
- 分阶段实现，先实现单智能体，再扩展为多智能体
- 使用成熟的状态机框架（如 LangGraph 风格）
- 充分的单元测试和集成测试

### Risk 3: 工具系统维护成本高
**缓解措施**:
- 工具接口标准化，易于扩展
- 工具实现模块化，独立测试
- 文档完善，降低维护成本

### Risk 4: 会话持久化存储成本
**缓解措施**:
- 实现数据清理策略（任务结束后7天自动清理）
- 检查点压缩存储
- 支持用户手动清理

### Risk 5: 实时通信性能问题
**缓解措施**:
- 使用消息队列缓冲（如 Redis Stream）
- 实现消息优先级和限流
- 前端实现消息去重和缓存

## Migration Plan

### Phase 1: 基础沙箱系统（2周）
- 集成 E2B SDK 和 API
- 实现 E2B 沙箱创建和管理
- 实现基础桌面环境访问（E2B 已提供 XFCE4 + VNC + Chromium）
- 实现基础工具（5-10个核心工具）
- 保留 Docker 实现代码（但不使用）

### Phase 2: 多智能体系统（3周）
- 实现 Planner Agent
- 实现 Executor Agent
- 实现基础协作机制

### Phase 3: 工具生态系统（4周）
- 实现所有 27 种工具
- 实现工具注册和发现机制
- 实现工具链式调用

### Phase 4: 持久化和流式交互（2周）
- 实现会话持久化
- 实现检查点机制
- 实现流式交互系统

### Phase 5: 前端界面（3周）
- 实现虚拟电脑 UI
- 实现任务监控界面
- 集成 WebSocket/SSE

### 总计: 14周（约3.5个月）

## Open Questions

1. **E2B 平台成本控制**？
   - 当前决策：使用 E2B 作为主要方案，监控使用量和成本
   - 成本优化：实现沙箱复用、预热池、智能调度等机制
   - 未来考虑：如果成本过高，可评估自建 Firecracker 方案或迁移到 Docker

2. **工具数量是否必须达到 27 种**？
   - 当前决策：分阶段实现，先实现核心工具（15-20种），再逐步扩展
   - 优先级：浏览器工具 > 终端工具 > 文件系统工具 > 代码执行工具 > 系统工具

3. **会话持久化最长支持多久**？
   - 当前决策：最长14天（与 Manus 一致）
   - 未来考虑：根据实际需求调整

4. **是否支持多用户并发**？
   - 当前决策：支持，每个用户独立的沙箱实例
   - 资源限制：每个沙箱的资源限制可配置

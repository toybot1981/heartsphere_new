# Design: 更新项目上下文文档

## Context

当前的 `openspec/project.md` 是模板文件，缺少实际的项目信息。为了帮助 AI 助手在创建 OpenSpec change proposal 时更好地理解项目上下文，需要基于现有的开发规范文档来丰富这个文件。

## Goals

1. **提供项目背景信息**：让 AI 助手了解心域系统的目的和核心功能
2. **明确技术栈**：列出后端、前端、AI服务等技术栈
3. **规范代码风格**：基于开发规范文档，提供代码风格和命名规范
4. **说明架构模式**：描述项目的架构设计原则和模式
5. **定义测试策略**：说明测试类型、工具和覆盖率要求
6. **规范工作流**：说明 Git 工作流和代码提交规范
7. **提供领域上下文**：说明心域系统的核心概念和功能模块
8. **列出约束和依赖**：说明技术约束和外部依赖

## Non-Goals

- 不创建新的规范文档
- 不修改现有的开发规范文档
- 不涉及代码实现
- 不创建 spec deltas（project.md 是上下文文档，不是规范文档）

## Decisions

### 决策1：内容来源
**决定**：主要基于 `docs/12-开发指南/开发规范/心域开发指南.md`，补充 `docs/12-开发指南/开发规范/插件开发规范.md` 中的插件相关内容。

**理由**：
- 心域开发指南是核心开发规范文档，包含完整的项目信息
- 插件开发规范提供插件系统的特定信息
- 确保与现有规范文档的一致性

### 决策2：内容组织
**决定**：按照 OpenSpec project.md 模板的结构组织内容，但填充实际项目信息。

**理由**：
- 保持与 OpenSpec 标准格式的一致性
- 便于 AI 助手快速定位信息
- 结构清晰，易于维护

### 决策3：详细程度
**决定**：提供足够的细节，但不重复完整的规范文档内容。引用规范文档作为详细参考。

**理由**：
- project.md 应该简洁，提供关键信息
- 详细规范在开发规范文档中
- 通过引用保持文档间的关联

## Risks / Trade-offs

### 风险1：内容过时
**风险**：项目技术栈或规范更新后，project.md 可能过时。

**缓解措施**：
- 在 project.md 中引用规范文档，鼓励查看最新规范
- 定期审查和更新 project.md

### 风险2：信息重复
**风险**：project.md 和开发规范文档可能存在信息重复。

**缓解措施**：
- project.md 提供摘要和关键信息
- 详细规范引用开发规范文档
- 明确文档的职责边界

## Migration Plan

1. **阶段1**：创建更新后的 project.md 内容
2. **阶段2**：验证内容完整性和准确性
3. **阶段3**：替换现有的 project.md
4. **阶段4**：验证 OpenSpec 工具正常工作

# Change: Enhance Guest Mode Access Logic

## Why

当前游客模式实现较为简单，仅在前端标记为游客，无法提供完整的用户体验。需要改进游客模式，使其：
1. 创建真实的临时用户账号，支持完整的登录流程
2. 提供体验会员类型，给予游客有限的Token配额体验系统功能
3. 限制游客只能使用预置的角色和场景，无法创建自定义内容
4. 支持游客平滑升级为正式用户，保留游客期间的数据

## What Changes

### Core Changes

- **MODIFIED**: 游客登录逻辑 - 自动创建临时用户并完成登录
- **ADDED**: 体验会员类型（Trial Membership）- 默认1万文本Token，其他配额为0
- **ADDED**: 游客权限控制 - 限制只能与预置角色交互，其他功能需注册
- **ADDED**: 游客预置内容 - 固定使用"日常生活助手"场景和6个角色
- **ADDED**: 游客升级功能 - 游客可直接注册升级为正式用户
- **MODIFIED**: 记忆生成逻辑 - 游客模式下不记录记忆

### Database Changes

- **ADDED**: `memberships` 表新增体验会员记录
- **MODIFIED**: 用户创建逻辑，自动为游客分配体验会员

### API Changes

- **ADDED**: 独立的游客登录接口 - `POST /api/auth/guest-login`（与正式用户登录接口分离）
- **ADDED**: 独立的游客注册接口 - `POST /api/auth/guest-register`（与正式用户注册接口分离）
- **ADDED**: 权限检查 - 在各个功能接口中添加游客权限验证
- **MODIFIED**: 记忆服务 - 跳过游客用户的记忆生成
- **MODIFIED**: 场景和角色访问逻辑 - 游客不关联个人场景和角色，直接使用系统预置内容

## Impact

- **Affected specs**: 
  - 用户认证（authentication）
  - 会员管理（membership-management）
  - 权限控制（access-control）
  - 角色交互（character-interaction）
  - 记忆系统（memory-system）

- **Affected code**:
  - `AuthController` - 游客登录逻辑
  - `MembershipService` - 体验会员创建和管理
  - 各功能Controller - 添加权限检查
  - `MemoryManager` - 跳过游客记忆生成
  - 前端登录流程 - 游客模式处理

- **Database**:
  - `memberships` 表 - 新增体验会员类型
  - `users` 表 - 游客用户记录

## Design Principles

1. **接口隔离**: 游客和正式用户使用完全独立的登录/注册接口，避免混淆
2. **预置内容**: 游客不关联个人场景和角色，所有游客统一使用系统硬编码的预置场景和角色
3. **无缝体验**: 游客登录应该像正式用户一样顺畅，但后台自动创建临时账号
4. **功能限制**: 明确限制游客可使用的功能，引导用户注册
5. **数据保护**: 游客模式下不保存长期数据（如记忆），但保留对话记录用于升级后使用
6. **平滑升级**: 游客升级为正式用户时，应该无缝迁移数据
7. **资源隔离**: 游客只能访问预置的场景和角色，无法修改系统内容

## User Experience Flow

1. **游客登录**: 用户选择"游客模式" → 调用 `POST /api/auth/guest-login` → 系统自动创建临时用户 → 分配体验会员 → 登录成功
2. **游客注册**: 游客选择"注册为正式用户" → 调用 `POST /api/auth/guest-register` → 更新用户信息 → 升级会员类型 → 初始化个人场景和角色
3. **功能使用**: 游客可以：
   - 与预置角色（时小光等6个）进行对话（使用系统预置场景ID: 50）
   - 使用1万文本Token额度
   - 查看对话记录
   - **注意**: 游客不拥有个人场景和角色，所有游客共享系统预置内容
4. **功能限制**: 尝试使用受限功能时：
   - 添加场景/角色 → 提示注册
   - 访问共享空间 → 提示注册
   - 撰写日记 → 提示注册
   - 查看记忆 → 提示注册（游客不生成记忆）
5. **升级流程**: 游客注册为正式用户 → 更新用户信息 → 迁移对话数据 → 初始化个人场景和角色

## Risks & Mitigation

- **风险1**: 游客账号滥用（创建大量临时账号）
  - **缓解**: 限制单个IP的游客账号创建频率
  - **缓解**: 游客账号设置过期时间（如30天未使用自动清理）

- **风险2**: Token配额被快速消耗
  - **缓解**: 体验会员Token配额较小（1万）
  - **缓解**: 监控异常消耗并限制

- **风险3**: 数据迁移复杂度
  - **缓解**: 设计简单的数据迁移逻辑，仅迁移对话记录
  - **缓解**: 提供清晰的数据迁移提示

## Success Criteria

- [ ] 游客使用独立的登录接口 `POST /api/auth/guest-login`（与正式用户接口分离）
- [ ] 游客使用独立的注册接口 `POST /api/auth/guest-register`（与正式用户接口分离）
- [ ] 游客登录自动创建临时用户并分配体验会员
- [ ] 游客不关联个人场景和角色，直接使用系统预置内容（场景ID: 50，角色ID: 315-320）
- [ ] 游客可以正常与预置角色对话
- [ ] 游客无法访问受限功能（添加场景、共享空间等）
- [ ] 游客升级为正式用户时数据正确迁移，并初始化个人场景和角色
- [ ] 游客模式下不生成记忆记录
- [ ] 游客预置场景和角色正确配置（硬编码）

# Design: Enhance Mentis with Manus-style Capabilities

## Context

参照 Manus AI 的成功实现，提升 Mentis 系统的能力。Manus AI 使用了 E2B 虚拟机平台、多智能体架构和27种工具，实现了强大的 AI Agent 能力。

当前 Mentis 系统已有基础的任务分解和执行能力，但缺少：
1. 任务与对话的明确关联
2. 完整的工具系统
3. 多样化的结果展示能力
4. E2B MCP 集成

## Goals / Non-Goals

### Goals
- 实现任务与对话的关联，任务列表只显示当前对话的任务
- 提供 Manus 风格的打对勾任务展示方式
- 构建完整的27种工具系统
- 支持多种结果展示形式（文本、列表、表格、图表、图片）
- 集成 E2B MCP Gateway，扩展 E2B 能力
- 实现虚拟机与对话的实时关联和查看

### Non-Goals
- 不实现 Manus 的多智能体架构（Planner/Executor/Monitor）
- 不实现 Manus 的会话持久化（14天）功能
- 不实现 Manus 的自动错误恢复机制（当前阶段）

## Decisions

### Decision 1: 任务与对话关联方式
**选择**: 在 `MentisTask` 实体中添加 `messageId` 字段，直接关联生成任务的用户消息。

**理由**:
- 简单直接，易于实现
- 查询效率高（通过索引）
- 符合当前数据库设计模式

**替代方案**: 使用 `executionId` 关联，但 `executionId` 可能跨多个用户消息。

### Decision 2: 工具系统架构
**选择**: 使用接口 + 注册表模式，每个工具实现 `Tool` 接口，统一注册到 `ToolRegistry`。

**理由**:
- 易于扩展新工具
- 统一的工具调用接口
- 便于工具管理和测试

**替代方案**: 使用策略模式或工厂模式，但注册表模式更简单直接。

### Decision 3: 结果展示方式
**选择**: 使用组件化方式，每种结果类型对应一个展示组件，自动识别结果格式。

**理由**:
- 组件化易于维护和扩展
- 自动识别减少用户配置
- 支持混合格式展示

**替代方案**: 使用单一组件根据类型切换，但组件化更清晰。

### Decision 4: E2B MCP 集成方式
**选择**: 在 E2B Bridge Service 中集成 MCP Gateway，Java 后端通过 Bridge Service 调用 MCP。

**理由**:
- E2B SDK 是 JavaScript/TypeScript，通过 Bridge Service 可以复用现有架构
- 避免在 Java 中直接实现 MCP 客户端
- Bridge Service 已经存在，扩展成本低

**替代方案**: 在 Java 后端直接实现 MCP 客户端，但需要更多开发工作。

## Risks / Trade-offs

### Risk 1: 工具系统复杂度
**风险**: 27种工具的实现和维护成本较高。

**缓解措施**:
- 分阶段实现，优先实现核心工具
- 使用统一的工具接口，减少重复代码
- 完善的单元测试和文档

### Risk 2: E2B MCP 依赖
**风险**: E2B MCP Gateway 可能不稳定或变更。

**缓解措施**:
- 封装 MCP 调用，便于后续替换
- 提供降级方案，MCP 不可用时使用基础工具
- 监控 MCP 连接状态

### Risk 3: 结果展示性能
**风险**: 复杂的结果展示（如图表）可能影响前端性能。

**缓解措施**:
- 使用懒加载和代码分割
- 图表渲染使用 Web Worker
- 限制单次展示的数据量

### Risk 4: 数据库迁移
**风险**: 添加 `message_id` 字段可能影响现有数据。

**缓解措施**:
- 字段设为可空，允许历史数据
- 提供数据迁移脚本，为历史任务补充 `message_id`
- 分阶段部署，先添加字段，再更新逻辑

## Migration Plan

### Phase 1: 数据库迁移（1天）
1. 创建数据库迁移脚本，添加 `message_id` 字段（可空）
2. 更新 `MentisTask` 实体类
3. 为历史任务补充 `message_id`（可选）

### Phase 2: 任务关联（2天）
1. 修改任务创建逻辑，关联 `messageId`
2. 修改任务查询逻辑，只返回当前对话的任务
3. 更新前端任务展示组件

### Phase 3: 工具系统（2周）
1. 实现工具接口和注册表
2. 分批次实现27种工具（每批5-6种）
3. 集成工具系统到执行引擎

### Phase 4: 结果展示（1周）
1. 实现各种结果展示组件
2. 实现结果格式识别逻辑
3. 集成到对话界面

### Phase 5: E2B MCP（1周）
1. 在 Bridge Service 中添加 MCP Gateway 支持
2. 实现 MCP 客户端调用
3. 集成 MCP 工具到工具系统

### Rollback Plan
- 数据库迁移可回滚（删除字段）
- 代码变更通过版本控制回滚
- 功能开关控制新功能启用/禁用

## Open Questions

1. **工具执行超时**: 工具执行超时时间如何设置？是否需要用户可配置？
   - **建议**: 默认超时时间根据工具类型设置（浏览器工具30秒，终端工具60秒），支持任务级别配置。

2. **结果展示优先级**: 当结果包含多种格式时，如何确定展示优先级？
   - **建议**: 按照图表 > 表格 > 列表 > 文本 > 图片的顺序，优先展示结构化数据。

3. **MCP 工具缓存**: MCP 工具列表是否需要缓存？缓存时间多长？
   - **建议**: 缓存工具列表5分钟，工具变更时主动刷新。

4. **虚拟机实时查看频率**: 虚拟机屏幕刷新频率如何设置？
   - **建议**: 默认3秒，用户可配置（1-10秒），执行中自动提高频率。

5. **历史任务查看**: 用户是否需要查看历史任务？如果需要，如何访问？
   - **建议**: 当前阶段不提供历史任务查看，后续可添加"任务历史"页面。

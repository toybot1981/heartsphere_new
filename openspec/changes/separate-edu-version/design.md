# Design: Separate Education Edition to Independent Client

## Context

当前教育版（edu）版本已经初步创建了独立的前端和后端结构，但存在代码分散、架构不清晰、admin 管理模块未实现等问题。需要将 edu 版本完全分离为独立客户端，并建立完整的管理体系。

**背景约束**：
- `frontend-edu/` 和 `admin-edu/` 目录仍然存在，需要统一到 `edu/` 目录
- admin 后端中的 edu 管理模块已创建基础结构，但大部分功能处于待实现状态
- 需要基于现有实现和未来数字人在教育领域的应用场景进行规划
- 必须确保数据隔离和独立部署能力

## Goals / Non-Goals

### Goals
- **完全独立**：edu 前端和后端完全独立，可独立部署和迭代
- **代码整合**：统一 `frontend-edu/` 和 `admin-edu/` 到 `edu/` 目录结构
- **admin 管理完善**：实现 admin 后端 edu 管理模块的所有功能，通过 API 调用 edu 后端
- **数字人规划**：设计数字人在教育领域的应用架构，为未来扩展奠定基础
- **数据隔离**：确保 edu 数据库与主系统完全隔离，admin 通过 API 访问

### Non-Goals
- **不合并主系统**：edu 系统保持独立，不与主系统合并
- **不共享数据库**：不使用主系统数据库，保持完全独立
- **不过度抽象**：在共享模块中保持简单，不创建过度复杂的抽象层
- **不实现所有数字人功能**：当前阶段只规划架构，具体实现放在后续阶段

## Decisions - Part 1: Core Architecture

### Decision 1: 目录结构统一策略

**决策**：将 `frontend-edu/` 代码迁移到 `edu/frontend/`，将 `admin-edu/` 代码整合到 `admin/frontend/src/pages/edu/`

**理由**：
- `edu/` 目录已经存在，符合项目整体结构
- admin-edu 本质上是 admin 管理后台的一部分，应该整合到 admin/frontend
- 避免代码重复，便于维护

**备选方案**：
- 保持 `frontend-edu/` 和 `admin-edu/` 独立：会导致目录混乱，不符合项目结构规范
- 将 `admin-edu/` 也放到 `edu/` 目录：admin 管理应该统一在 admin 目录下

### Decision 2: Admin 与 Edu 后端通信方式

**决策**：Admin 后端通过 HTTP REST API 调用 Edu 后端服务，不直接访问 Edu 数据库

**理由**：
- 保持系统边界清晰，edu 系统独立管理自己的数据
- 通过 API 调用可以实现服务间解耦，便于独立部署和扩展
- 符合微服务架构原则，edu 可以独立演进

**实现方式**：
- 使用 Spring RestTemplate 或 WebClient 进行 HTTP 调用
- 在 admin 后端配置 edu 后端的 base URL（通过配置文件）
- 统一错误处理和重试机制

**备选方案**：
- Admin 直接访问 Edu 数据库：违反服务边界，增加耦合，不利于独立部署
- 使用消息队列（MQ）：对于管理操作，同步 API 调用更合适

### Decision 3: 共享模块使用策略

**决策**：edu 系统通过 `shared` 模块复用基础能力，但业务逻辑完全独立

**复用内容**：
- AI 服务接口（通过 shared 定义的接口，实际调用统一的 AI 服务）
- 认证授权基础框架（JWT、Spring Security 基础配置）
- 通用 DTO 和工具类
- 文件上传存储服务

**独立内容**：
- 业务实体和仓库（edu 特定的数据模型）
- 业务服务逻辑（学生、教师、课程等管理）
- 前端页面和组件（edu 特定的 UI）

**理由**：
- 避免重复实现基础功能，降低维护成本
- 保持业务逻辑独立，便于针对性优化
- 符合 shared 模块的定位（定义接口和类型，不包含业务逻辑）

## Decisions - Part 2: Digital Human Education Architecture

### Decision 4: 数字人教育应用架构

**决策**：基于现有角色系统扩展，创建教育版专用的数字人角色体系

**架构设计**：
- **EduCharacter 实体**：继承或参考主系统的 Character 概念，增加教育相关属性
  - 角色类型：教学助手、学习伙伴、心理辅导、作业辅导、学科讲解
  - 适用年龄段：6-12岁（小学）、13-18岁（中学）
  - 学科标签：数学、语文、英语等
- **EduCharacterInteraction 实体**：记录学生与数字人的互动
  - 互动类型：教学对话、作业辅导、心理疏导、知识讲解
  - 学习内容记录：对话内容、学习知识点、理解程度
  - 学习效果评估：学习时长、理解度评分、学习进度
- **DigitalHumanService**：教育版数字人服务
  - 根据学生年龄和兴趣推荐合适的数字人
  - 根据学科和学习目标创建专业数字人
  - 管理数字人与学生的互动历史

**理由**：
- 复用主系统的角色概念，降低学习成本
- 针对教育场景扩展，满足教育特定需求
- 为未来深度应用预留扩展空间

**备选方案**：
- 完全独立的数字人系统：重复实现，维护成本高
- 直接使用主系统角色：无法满足教育场景的特定需求

## Decisions - Part 3: Data Isolation and Phased Implementation

### Decision 5: 数据库隔离策略

**决策**：使用独立的数据库 `heartsphere_edu`，与主系统数据库完全隔离

**表设计原则**：
- 表名统一使用 `edu_` 前缀（如 `edu_students`、`edu_teachers`）
- 使用 Flyway 进行数据库版本管理
- 独立的数据库连接配置
- 支持独立备份和恢复

**理由**：
- 确保数据完全隔离，避免误操作影响主系统
- 便于独立部署和扩展
- 符合数据安全合规要求（教育数据需要特别保护）

**备选方案**：
- 使用同一数据库但不同 schema：仍然在同一数据库实例，隔离不够彻底
- 使用同一数据库同一 schema 但不同表前缀：不符合独立部署的要求

### Decision 6: 分阶段实施策略

**决策**：分 5 个阶段实施，每个阶段有明确的可交付成果

**阶段划分**：
1. **Phase 1：代码整理和迁移**（1-2周）- 基础结构搭建
2. **Phase 2：完善 admin edu 管理模块**（2-3周）- 管理能力完善
3. **Phase 3：数字人教育应用规划**（1周）- 架构设计
4. **Phase 4：实现数字人教育功能**（4-6周）- 核心功能实现
5. **Phase 5：测试和优化**（1-2周）- 质量保障

**理由**：
- 内容过多，分阶段实施降低风险，便于管理
- 每个阶段有独立的可交付成果，便于验收
- 可以在每个阶段后进行评审和调整

## Risks / Trade-offs

### Risk 1: 代码迁移可能引入 bug
**风险**：迁移 `frontend-edu/` 和 `admin-edu/` 代码时可能遗漏某些依赖或配置
**缓解措施**：
- 迁移后进行全面测试
- 保留原目录一段时间作为备份
- 使用 Git 进行版本控制，便于回滚

### Risk 2: Admin 与 Edu 后端通信延迟
**风险**：通过 HTTP API 调用可能增加延迟，影响管理操作体验
**缓解措施**：
- 使用连接池和请求缓存优化性能
- 对于批量操作，考虑使用异步处理
- 监控 API 调用性能，设置合理的超时时间

### Risk 3: 共享模块版本冲突
**风险**：edu 系统和主系统使用不同版本的 shared 模块可能导致兼容性问题
**缓解措施**：
- 统一使用 shared 模块的版本管理
- shared 模块保持向后兼容
- 破坏性变更需要同时更新所有依赖方

### Risk 4: 数字人功能实现复杂度高
**风险**：数字人教育应用涉及多个复杂功能，可能超出预期工作量
**缓解措施**：
- Phase 3 进行详细规划，评估工作量
- Phase 4 分小步骤实现，每个步骤独立测试
- 如果复杂度超出预期，可以将部分功能延后到后续版本

### Trade-off: 完全独立 vs 代码复用
**权衡**：完全独立可以降低耦合，但可能增加代码重复
**决策**：选择在共享模块中复用基础能力，业务逻辑保持独立
**理由**：平衡了独立性和代码复用，符合项目的 shared 模块设计原则

### Trade-off: Admin 直接访问数据库 vs API 调用
**权衡**：直接访问数据库性能更好，但增加了耦合
**决策**：选择 API 调用方式
**理由**：虽然增加了延迟，但保持了系统边界清晰，便于独立部署和扩展

## Migration Plan

### Step 1: 代码迁移（Phase 1）
1. 备份 `frontend-edu/` 和 `admin-edu/` 目录
2. 迁移 `frontend-edu/` 代码到 `edu/frontend/`
3. 迁移 `admin-edu/` 页面到 `admin/frontend/src/pages/edu/`
4. 更新所有 import 路径和配置
5. 测试确保功能正常
6. 清理原目录（标记为废弃，保留一段时间后删除）

### Step 2: Admin 后端集成（Phase 2）
1. 在 admin 后端配置 edu 后端 base URL
2. 创建 EduBackendClient 用于 HTTP 调用
3. 实现 AdminEduStudentService 所有方法
4. 实现 AdminEduTeacherService 所有方法
5. 实现 AdminEduContentService 所有方法
6. 实现 AdminEduAnalyticsService 所有方法
7. 完善 admin frontend 的 edu 管理界面
8. 端到端测试

### Step 3: 数字人架构设计（Phase 3）
1. 设计 EduCharacter 实体结构
2. 设计 EduCharacterInteraction 实体结构
3. 设计 DigitalHumanService 接口
4. 编写详细的技术方案文档
5. 评审和确认

### Step 4: 数字人功能实现（Phase 4）
1. 创建数据库表结构（Flyway 迁移脚本）
2. 实现 EduCharacter 实体和仓库
3. 实现 EduCharacterInteraction 实体和仓库
4. 实现 DigitalHumanService 服务
5. 实现前端数字人相关组件
6. 集成到现有功能中
7. 单元测试和集成测试

### Step 5: 测试和优化（Phase 5）
1. 端到端功能测试
2. 性能测试和优化
3. 安全审计
4. 文档完善
5. 用户验收测试

### Rollback Plan
- 每个阶段完成后进行 Git 提交，保留回滚点
- 如果某个阶段出现问题，可以回滚到上一阶段
- 保留原 `frontend-edu/` 和 `admin-edu/` 目录一段时间，确保可以快速恢复

## Open Questions

1. **AI 服务调用方式**：
   - edu 系统是否直接调用主系统的 AI 服务？
   - 还是通过统一的 AI 服务网关？
   - **建议**：通过 shared 模块定义的接口调用，实际部署时可以使用同一 AI 服务实例

2. **用户认证和授权**：
   - edu 系统的用户是否与主系统用户共享？
   - 还是完全独立的用户体系？
   - **建议**：当前阶段使用独立用户体系，未来可以考虑 SSO 单点登录

3. **文件存储策略**：
   - edu 系统的文件存储是否与主系统分离？
   - 还是使用同一存储服务但不同路径前缀？
   - **建议**：使用同一存储服务（如 MinIO/OSS），但使用不同的路径前缀（`edu/`）进行隔离

4. **部署环境**：
   - edu 系统是否与主系统部署在同一服务器？
   - 还是完全独立的部署环境？
   - **建议**：开发环境可以同一服务器，生产环境建议独立部署以确保隔离

5. **数字人角色来源**：
   - 数字人角色是系统预置还是用户可以创建？
   - **建议**：系统预置基础教学角色（数学老师、语文老师等），用户也可以创建个性化学习伙伴角色

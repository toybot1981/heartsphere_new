# Design: 优化CORS配置

## Context

当前项目有67个Controller使用了 `@CrossOrigin` 注解，违反了新制定的CORS配置规范。规范要求：
1. 所有CORS配置统一在 `WebSecurityConfig` 中管理
2. Controller层禁止使用 `@CrossOrigin` 注解
3. 使用环境配置区分开发和生产环境

## Goals

1. **符合规范**: 移除所有Controller上的 `@CrossOrigin` 注解
2. **统一配置**: 所有CORS配置集中在 `WebSecurityConfig` 中
3. **环境区分**: 支持开发和生产环境的不同配置
4. **功能完整**: 确保所有必要的请求头和响应头都已配置

## Non-Goals

- 不改变CORS的行为（允许的来源、方法、请求头等）
- 不添加新的CORS功能
- 不修改前端代码

## Decisions

### 决策1：批量移除策略
**决定**: 使用脚本批量移除所有Controller上的 `@CrossOrigin` 注解，然后手动验证

**理由**:
- 67个文件手动修改工作量太大
- 使用脚本可以确保一致性
- 需要手动验证确保没有遗漏

### 决策2：全局配置优化
**决定**: 在 `WebSecurityConfig` 中添加环境配置支持，明确列出所有需要的请求头

**理由**:
- 符合规范要求
- 便于维护和管理
- 支持不同环境的配置

### 决策3：自定义请求头处理
**决定**: 检查项目中使用的自定义请求头，在全局配置中明确添加

**理由**:
- 确保所有自定义请求头都被允许
- 避免未来出现CORS错误

## Risks / Trade-offs

### 风险1：遗漏某些特殊配置
**风险**: 某些Controller可能有特殊的CORS需求，移除注解后可能失效

**缓解措施**:
- 检查是否有Controller使用了特殊的CORS配置（如特定的origins）
- 如果有，需要在全局配置中支持

### 风险2：环境配置错误
**风险**: 生产环境配置错误可能导致CORS问题

**缓解措施**:
- 使用环境变量配置
- 提供默认值（开发环境）
- 在部署文档中说明配置方法

### 风险3：测试不充分
**风险**: 移除注解后可能某些API请求失败

**缓解措施**:
- 运行完整的测试套件
- 手动测试关键API
- 检查浏览器控制台的CORS错误

## Migration Plan

1. **阶段1**: 检查当前配置，识别所有自定义请求头
2. **阶段2**: 优化全局CORS配置，添加环境支持
3. **阶段3**: 批量移除Controller上的 `@CrossOrigin` 注解
4. **阶段4**: 测试验证，确保所有API正常工作
5. **阶段5**: 更新相关文档（如需要）

## Open Questions

- 是否有Controller使用了特殊的CORS配置（如特定的origins）？
- 生产环境允许的来源列表是什么？
- 是否需要暴露某些自定义响应头？

# Design: Python 执行机制分析与设计

## Context

当前系统中存在多种 Python 执行方式：

1. **直接执行（PythonScriptExecutor）**：
   - 使用 `ProcessBuilder` 直接调用系统 `python3` 命令
   - 适用于本地环境，无需虚拟机
   - 受限于本地 Python 环境和依赖

2. **虚拟机执行（VmPythonScriptExecutor）**：
   - 在 E2B 虚拟机中执行 Python 脚本
   - 支持自动安装依赖，环境隔离
   - 需要虚拟机资源，有性能开销

3. **技能系统执行（ScriptSkillExecutor）**：
   - 当前为模拟实现，未真正执行
   - 需要实现真实的 Python 执行能力

4. **工具执行（PythonRunTool）**：
   - 通过 `ComputerUseExecutor` 执行
   - 根据配置选择直接执行或虚拟机执行

## Goals / Non-Goals

### Goals
- 统一 Python 执行接口，消除代码重复
- 根据场景自动选择最优执行策略
- 提供安全机制和资源限制
- 支持配置管理和策略切换
- 保持向后兼容，不影响现有功能

### Non-Goals
- 不强制迁移所有现有代码（渐进式迁移）
- 不改变现有的执行结果格式
- 不引入新的外部依赖（如 Jython）

## Decisions

### Decision 1: 统一执行接口

**选择**：创建统一的 `PythonExecutionService` 接口，所有 Python 执行都通过此接口

**理由**：
- 消除代码重复，统一管理
- 便于添加新的执行策略
- 统一错误处理和日志记录

**替代方案**：
- 保持现状：各模块独立实现
  - 缺点：代码重复，维护困难
- 使用策略模式：每个执行方式作为策略
  - 缺点：需要额外的策略选择逻辑

### Decision 2: 执行策略选择机制

**选择**：基于配置和场景自动选择执行策略

**策略选择规则**：
1. **配置优先**：如果配置明确指定执行方式，使用配置
2. **场景判断**：
   - 需要隔离环境或自动安装依赖 → 虚拟机执行
   - 简单脚本，本地有环境 → 直接执行
   - 技能系统 → 统一接口执行
3. **降级策略**：直接执行失败时，自动降级到虚拟机执行

**替代方案**：
- 固定使用虚拟机：安全但性能开销大
- 固定使用直接执行：性能好但受限于本地环境

### Decision 3: 安全机制

**选择**：多层安全防护

1. **输入验证**：检查脚本内容，禁止危险操作
2. **资源限制**：
   - 执行超时（可配置）
   - 内存限制（虚拟机执行）
   - CPU 限制（虚拟机执行）
3. **沙箱隔离**：虚拟机执行提供天然隔离
4. **审计日志**：记录所有执行请求和结果

**替代方案**：
- 仅依赖虚拟机隔离：安全但性能开销大
- 仅输入验证：性能好但安全性较低

### Decision 4: 配置管理

**选择**：支持多级配置（系统级、会话级、请求级）

**配置项**：
- 默认执行策略（直接执行/虚拟机执行）
- 超时时间
- 资源限制
- 允许的 Python 库白名单
- 禁止的操作黑名单

**替代方案**：
- 硬编码配置：简单但不够灵活
- 仅数据库配置：灵活但需要数据库访问

## Architecture

### 统一执行接口

```
PythonExecutionService (接口)
├── executeScript(request) → ScriptResult
├── getSupportedStrategies() → List<Strategy>
└── selectStrategy(request) → Strategy

实现类：
├── DirectPythonExecutor (直接执行)
├── VmPythonExecutor (虚拟机执行)
└── StrategySelector (策略选择器)
```

### 执行流程

```
1. 接收执行请求
   ↓
2. 验证请求参数
   ↓
3. 选择执行策略
   ↓
4. 执行 Python 脚本
   ↓
5. 收集执行结果
   ↓
6. 记录审计日志
   ↓
7. 返回结果
```

### 策略选择逻辑

```
请求 → 配置检查 → 场景判断 → 策略选择
                      ↓
                  直接执行/虚拟机执行
                      ↓
                  执行失败 → 降级策略
```

## Risks / Trade-offs

### 风险 1: 性能开销
- **风险**：统一抽象层可能引入额外开销
- **缓解**：优化实现，减少不必要的对象创建和转换

### 风险 2: 迁移复杂度
- **风险**：重构可能影响现有功能
- **缓解**：渐进式迁移，保持向后兼容，充分测试

### 风险 3: 策略选择错误
- **风险**：自动选择可能不是最优策略
- **缓解**：提供配置覆盖，允许手动指定策略

### 风险 4: 安全漏洞
- **风险**：直接执行可能存在安全风险
- **缓解**：多层安全防护，默认使用虚拟机执行

## Migration Plan

### 阶段 1: 分析和设计（当前阶段）
- 梳理现有实现
- 设计统一接口
- 制定迁移计划

### 阶段 2: 实现统一接口
- 创建 `PythonExecutionService` 接口
- 实现策略选择器
- 保持现有实现作为实现类

### 阶段 3: 迁移调用方
- 迁移 `PythonRunTool` 使用新接口
- 迁移技能系统使用新接口
- 保持其他调用方不变（向后兼容）

### 阶段 4: 优化和加固
- 性能优化
- 安全加固
- 配置管理完善

### 阶段 5: 清理和文档
- 移除废弃代码
- 更新文档
- 代码审查

## Open Questions

1. **是否需要支持 Python 2**？
   - 当前只支持 Python 3，是否需要兼容 Python 2？

2. **是否需要支持其他 Python 运行时**？
   - 如 PyPy、Jython 等

3. **配置管理方式**？
   - 使用数据库还是配置文件？

4. **执行结果格式**？
   - 是否需要统一结果格式，还是保持现有格式？
